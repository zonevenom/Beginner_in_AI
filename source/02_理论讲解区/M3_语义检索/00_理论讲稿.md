## 一、关键词搜索的三个死穴

你在文档里按 `Ctrl+F` 搜"退款"，这是关键词匹配：**字面一样才算命中**。

它会在三种情况下彻底失效：

| 情况 | 例子 | 结果 |
|---|---|---|
| **同义词** | 你搜"退货"，文档里写的是"退还商品" | 搜不到 |
| **跨语言** | 你搜"退款"，文档是英文 "refund policy" | 搜不到 |
| **表述不同** | 你搜"东西坏了能换吗"，文档写"商品质量问题支持换货" | 搜不到 |

而人不是这么找东西的。你说"东西坏了能换吗"，你脑子里已经知道这和"质量问题换货"是一回事——**你比的是"意思"，不是"字"。**

**语义检索要做的，就是让电脑也学会比"意思"。**

---

## 二、Embedding：把一句话变成一个"坐标"

### 核心比喻：把每句话放到一张巨大的地图上

想象有一张地图：

- 意思相近的句子，**住得近**
- 意思无关的句子，**住得远**

"如何申请退款"和"钱怎么退回来"，这两句话在这张地图上是**邻居**。
"如何申请退款"和"今天天气不错"，一个在城东一个在城西。

**Embedding（嵌入）就是"算出这句话在地图上的坐标"这件事。**

只不过这张地图不是 2 维的，而是 **几百到几千维**的（常见 768、1024、1536、3072）。人脑想象不了 1536 维，但电脑算距离毫无压力。

### 一句话定义

> **Embedding = 把一段文字，转换成固定长度的一串数字。这串数字代表它的"意思坐标"。**

```
"如何申请退款"  →  [0.021, -0.153, 0.887, ..., 0.004]   （1536 个数字）
"钱怎么退回来"  →  [0.019, -0.148, 0.879, ..., 0.011]   （很接近！）
"今天天气不错"  →  [-0.442, 0.771, 0.003, ..., 0.619]   （差很远）
```

### 为什么这招有效（不用公式的解释）

模型在训练时读过海量文本。它学到一件事：**"在相似的上下文里出现的词，意思应该相近"**。

比如"退款"和"退货"经常出现在同一类句子里，"退款"和"天气"几乎不一起出现。训练的結果就是：前者坐标接近，后者坐标远离。

> 这个思想叫"分布式假设"：**一个词的意思，由它周围常出现的词决定。**
> 你不需要记这个名字，只需要记住"**住得近 = 意思近**"。

## 三、怎么算"近"：余弦相似度

### 直觉

两个向量之间可以算"夹角"：

- 夹角**小**（方向一致）→ 相似度高，接近 1
- 夹角**90°**（垂直）→ 无关，接近 0
- 夹角**大**（方向相反）→ 负相关，接近 -1

**余弦相似度**就是这个夹角的余弦值，范围 -1 到 1。

### 为什么用"方向"而不是"距离"

因为**长度不重要，方向才重要**。

"退款"和"我要申请退款，因为商品有质量问题，希望尽快处理"——后者字数多、向量"长"，但它们说的是同一件事，**方向一致**。

用方向比，长短不影响；用直线距离比，长句子会被"冤枉"。

### 代码实现（三行）

```python
import numpy as np

def cosine(a, b):
    a, b = np.array(a), np.array(b)
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))
```

`a @ b` 是点积，`np.linalg.norm` 是长度。**看不懂没关系，你需要知道的是**：

> 如果先把所有向量"归一化"（长度都变成 1），那余弦相似度就等于**点积**，可以一次性批量算完，快几十倍。

```python
def normalize(v):
    v = np.array(v, dtype=np.float32)
    return v / (np.linalg.norm(v) + 1e-10)     # +1e-10 防止除以 0
```

> **`1e-10` 这个小尾巴是工程习惯**：万一模型返回了全 0 向量，不加它会得到 `nan`，然后你排查半天。

## 四、Embedding 从哪来：三个现实选择

### ⚠️ 一个你必须知道的事实

**不是所有大模型厂商都提供 embedding 接口。**

比如 DeepSeek 目前（以官网为准）主推对话模型，**没有 embedding 接口**。所以到 M3 你会发现：

> **"聊天"和"向量"往往是两个不同的服务，甚至两家不同的公司。**

这不是坏事，这是真实工程的样子。你的架构要能容纳"多厂商"。

### 三条路

| 方案 | 代表 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **A. 国内 API** | 智谱 `embedding-3`、阿里百炼 `text-embedding-v*` | 中文效果好、免部署、便宜 | 要注册新账号、要联网 | **推荐** |
| **B. 聚合平台** | 硅基流动等，OpenAI 兼容 | 一个 key 调多种模型 | 多一层中间商 | 备选 |
| **C. 本地模型** | `sentence-transformers` + `bge-small-zh` | 免费、离线、数据不外传 | 要下载几百 MB，CPU 慢一点 | 数据敏感时 |

**对你的建议**：先用 **A**（注册一个 embedding 服务），跑通全流程。等 M5 要反复做实验时，再考虑 C（省 API 调用费）。

> 🛑 **注册新账号、装新库之前，先跟我说。** 我会告诉你哪个最便宜、有没有免费额度。

### 调用长什么样（OpenAI 兼容格式）

```python
from openai import OpenAI

emb_client = OpenAI(
    api_key=os.getenv("EMBED_API_KEY"),
    base_url="https://open.bigmodel.cn/api/paas/v4",   # 以你选的厂商文档为准
)

resp = emb_client.embeddings.create(
    model="embedding-3",
    input=["如何申请退款", "钱怎么退回来", "今天天气不错"],
)

vectors = [d.embedding for d in resp.data]
```

**注意 `input` 可以是字符串列表**——一次传多条，比一条条调快得多、也便宜得多（很多厂商按次计费或有批量优惠）。

## 五、向量库：为什么不直接存成一个 list

你可以把所有向量存进一个 Python 列表，查询时暴力算一遍。**几十条数据完全够用。**

但数据一多就崩：

| 数据量 | 暴力算法（numpy） | 需要向量库吗 |
|---|---|---|
| 100 条 | 毫秒级 | 不需要 |
| 1 万条 | 几十毫秒 | 勉强 |
| 100 万条 | 几秒~几十秒 | **必须** |

向量库（Chroma、FAISS、Milvus、Qdrant…）帮你解决四件事：

| 能力 | 说明 |
|---|---|
| **近似最近邻（ANN）** | 不追求 100% 精确，用索引换速度，毫秒级返回 |
| **持久化** | 存硬盘，重启不丢 |
| **元数据过滤** | "只在 2024 年的文档里搜" |
| **增删改** | 不用每次全量重算 |

### 你只需要会四个动作

```python
import chromadb

client = chromadb.PersistentClient(path="./chroma_db")
col = client.get_or_create_collection("notes")

# ① 增
col.add(ids=["1", "2"], documents=["文本A", "文本B"], metadatas=[{"src": "a"}, {"src": "b"}])

# ② 查（传文本，它会自动用默认 embedding 函数；也可以自己传向量）
res = col.query(query_texts=["怎么退款"], n_results=3)

# ③ 删
col.delete(ids=["2"])

# ④ 看
print(col.count())
```

> ⚠️ **Chroma 默认会自己下一个 embedding 模型**，这会让你以为"我在用 API 的向量"，其实是两套东西混在一起。**一定要显式传入自己的向量**，否则你会得到莫名其妙的排序。

```python
col.add(ids=ids, documents=texts, embeddings=my_vectors)   # 显式传
res = col.query(query_embeddings=[q_vec], n_results=3)     # 显式查
```

> 这是新手在 Chroma 上最常踩的坑，没有之一。

## 六、五个决定效果的工程细节

这些细节，教程很少讲，但直接决定"你的搜索是不是好用"。

| 细节 | 说明 | 建议 |
|---|---|---|
| **① 归一化** | 存之前把所有向量长度变成 1 | 一定要做，省事又提速 |
| **② 批量** | 一次传 32/64 条，不要一条一条调 | 快 10 倍，还可能更便宜 |
| **③ 相似度阈值** | 低于某个分数就认为"没有相关内容" | 关键！否则永远返回 top-1，哪怕完全不相关 |
| **④ top-k 的选择** | k 太小漏，k 太大吵 | 3~5 起步，M5 再调 |
| **⑤ 文本要"干净"** | 去掉页眉页脚、乱码、重复空行 | 脏数据会污染向量 |

### 关于 ③ 阈值（最重要）

没有阈值的搜索，是"必须给你一个答案"的搜索。

用户问"怎么给猫剪指甲"，你的知识库全是退款政策。没有阈值 → 它会把最像的那条退款政策硬塞给你。用户看到的就是"这 AI 在胡说"。

```python
THRESHOLD = 0.5   # 需要按你的模型/数据实测调整

hits = [(s, t) for s, t in results if s >= THRESHOLD]
if not hits:
    return "抱歉，我的资料里没有相关内容。"
```

> **"敢说不知道"，是检索系统成熟的标志。** 这句话在 M4/M5 会反复出现。

## 七、语义检索的三个死穴（你必须知道）

语义检索不是万能药。它在下面这些场景会**输给**关键词搜索：

| 场景 | 为什么 | 例子 |
|---|---|---|
| **精确标识符** | 向量不理解"字符级"的精确匹配 | 搜订单号 `A20240315001`，语义检索可能返回一堆别的订单 |
| **否定与数量** | "不含糖"和"含糖"在向量空间非常接近 | 搜"不含防腐剂的食品"可能返回"含防腐剂" |
| **罕见专有名词** | 训练时没见过，向量不准 | 搜内部项目代号"凤凰计划" |

### 所以工业界的正确答案是：**混合检索**

关键词（BM25）+ 语义（向量），两路都跑，再合并排序。这叫 **Hybrid Search**，是 M5 的核心内容。

> 记住这个判断：**用户搜的是"概念"→ 用向量；用户搜的是"编号/代码/精确词"→ 用关键词；不知道 → 两个都用。**

## 【常见误解】

**误解 1："Embedding 是加密/压缩。"**
不是。它是**语义映射**，不可逆（你没法从向量还原原文），也不保证保真（相似的意思可能被映射得不够近）。

**误解 2："维度越高越好。"**
不一定。高维更细，但更慢更贵，而且**在数据量小时反而容易"过拟合噪声"**。中小规模用 512~1024 维足够。

**误解 3："相似度高就一定相关。"**
不一定。向量只捕捉"语义相近"，不捕捉"是否回答了问题"。问"退款流程"，可能召回"退款政策说明"——很像，但不是你要的。**这就是 M5 要上"重排（rerank）"的原因。**

**误解 4："用了向量库就不用管数据质量了。"**
完全相反。**垃圾进，垃圾出**，而且向量库会让垃圾看起来"很有道理"（因为它总能返回 top-3）。
