## 一、最大的误会：它不是"忘了"，是"根本没记"

新手最常问："我明明跟它说了我叫张三，它怎么又忘了？"

### 真相

**大模型是无状态的（stateless）。**

每次你调用 API，都是一次**全新的、互不相干的**请求。就像：

> 你去一家餐厅，每次都是一个全新的服务员，他不认识你，也不记得你上次点了什么。
> 你每次进门，都得重新自我介绍。

**它没有"会话"，没有"内存"，没有"上次"。** 服务器处理完你的请求，就把一切丢掉了。

### 那 ChatGPT 为什么记得？

因为**前端在帮你"复述"**。

每次你发新消息，它其实把你的**全部历史对话**重新打包发了一遍：

```
第 1 轮发过去：[我说：我叫张三]
第 2 轮发过去：[我说：我叫张三] [它说：你好张三] [我说：我叫什么？]
第 3 轮发过去：[我说：我叫张三] [它说：你好张三] [我说：我叫什么？] [它说：你叫张三] [我说：……]
```

**"记忆"是假象，"每次重发"是真相。**

> 这句话值一整个模块。你现在理解了，后面 RAG、Agent 都建立在同一个事实上。

### 代码上怎么实现

`messages` 就是一个**列表**，你每次把新的一问一答**追加**进去，再整包发过去：

```python
messages = [{"role": "system", "content": "你叫小助"}]

while True:
    q = input("你：")
    messages.append({"role": "user", "content": q})        # ① 追加你的话

    resp = client.chat.completions.create(model="deepseek-chat", messages=messages)

    answer = resp.choices[0].message.content
    messages.append({"role": "assistant", "content": answer})   # ② 追加它的话
    print("小助：", answer)
```

**就这两行 `append`，就是"记忆"的全部秘密。**

注意 ② 这一行：**必须把它自己的回答也存回去**。很多新手只存用户的话，结果模型不知道自己刚才说了什么，前后矛盾。

## 二、代价：上下文是会"滚雪球"的

### 算一笔账

假设每轮对话平均 200 token。到第 10 轮时，你发过去的是：

| 轮次 | 这一轮发过去的 token |
|---|---|
| 1 | 200 |
| 2 | 400 |
| 3 | 600 |
| … | … |
| 10 | 2000 |

**第 10 轮一次就发了 2000 token，是第 1 轮的 10 倍。**

10 轮下来总共发了：200+400+...+2000 = **11000 token**。

> 也就是说：**聊 10 轮 = 花了 55 轮的钱。** 对话越长，越贵，越慢。

### 这带来两个硬约束

| 约束 | 后果 |
|---|---|
| **上下文窗口有上限** | 超过就报错，或者最早的内容被截掉 |
| **成本是二次增长的** | 长对话贵得离谱，且延迟越来越高 |

所以真实产品里，**必须做截断**。不做截断的聊天机器人，一定会在某天崩掉。

## 三、截断策略：怎么"忘"得聪明

你不能简单粗暴地砍掉最早的内容——那会把 system（人设、规则）也砍掉，机器人立刻"失忆+变傻"。

### 四种策略，从简单到高级

#### 策略 1：只保留最近 N 轮（滑动窗口）⭐ 最常用

```python
MAX_TURNS = 10   # 保留最近 10 轮

def trim(messages, max_turns=10):
    system = messages[0]              # 永远保留 system
    history = messages[1:]
    # 每轮 = 1 条 user + 1 条 assistant
    keep = history[-max_turns * 2:]
    return [system] + keep
```

**优点**：简单、可控。
**缺点**：第 11 轮之前的事全忘了，用户会觉得"你怎么又忘了"。

#### 策略 2：按 token 数截断（更精确）

```python
def trim_by_tokens(messages, max_tokens=3000):
    system = messages[0]
    history = messages[1:]
    total = 0
    kept = []
    for m in reversed(history):        # 从最新的往回加
        t = len(m["content"]) // 2      # 粗略估算：1 token ≈ 2 个汉字
        if total + t > max_tokens:
            break
        kept.insert(0, m)
        total += t
    return [system] + kept
```

**为什么从后往前加**：因为**最近的话最重要**。

#### 策略 3：摘要压缩（高级）

把"很久以前"的对话，让模型**总结成一段话**，替代原文：

```
[早期对话摘要] 用户叫张三，是做电商的，正在调研 RAG 方案，预算有限。
[最近对话] ……
```

**优点**：几乎不丢信息。
**缺点**：要多调一次模型（花钱），实现复杂。

#### 策略 4：向量检索历史（更高级）

把历史对话存进向量库，每轮只检索"和当前问题最相关的几句"。

**这其实就是 RAG 用在对话历史上**——M4 学完你就懂了。

### 实践建议

| 场景 | 用什么 |
|---|---|
| 学习/练手 | 策略 1（滑动窗口） |
| 客服、助手类产品 | 策略 1 + 策略 3（近期原文 + 远期摘要） |
| 超长对话（如 AI 陪伴） | 策略 4 |

> **别一上来就做策略 3/4。** 策略 1 能撑住 90% 的场景。

## 四、流式输出：为什么它"看起来"更快

### 一个体验问题

非流式：用户点发送 → 转圈 8 秒 → 突然蹦出一大段字。
流式：用户点发送 → 1 秒后开始一个字一个字往外蹦 → 8 秒才蹦完。

**总时间一样，但体验天差地别。** 因为人最恨的是"没反应"，不是"慢"。

### 原理

模型本来就是**一个 token 一个 token 生成**的。非流式是"攒够了再一次性给你"，流式是"生成一个给你一个"。

技术上叫 **SSE（Server-Sent Events）**：服务器保持连接，持续往回推小块数据。

### 代码长什么样

```python
stream = client.chat.completions.create(
    model="deepseek-chat",
    messages=messages,
    stream=True,          # ← 只改这一个参数
)

full = ""
for chunk in stream:
    delta = chunk.choices[0].delta.content or ""
    print(delta, end="", flush=True)
    full += delta

# 注意：流式模式下拿不到完整的 usage，要自己估算或最后再查
```

### 三个坑

| 坑 | 现象 | 解法 |
|---|---|---|
| `delta.content` 可能是 `None` | 报 `TypeError` | `or ""` 兜底 |
| 流式拿不到完整 usage | 无法统计成本 | 自己按字数估算，或接受精度损失 |
| 拼接后内容重复/乱序 | 界面显示错乱 | 别用多线程同时写同一个变量 |

> **`print(..., flush=True)` 是必须的**。不加，Python 会攒一批才输出，你就看不到"逐字"效果了。

## 五、把体验做"像产品"的四个细节

这些不是炫技，是真实产品里必须有、但教程很少讲的东西。

| 细节 | 做法 | 为什么 |
|---|---|---|
| **① 首字延迟** | system 尽量短，历史尽量少 | 首字快 = 感觉快。用户感知的是"多久看到第一个字" |
| **② 中断能力** | 用户能点"停止生成" | 生成 500 字时用户已经知道答案了，不能停就是折磨 |
| **③ 失败要说人话** | 401 显示"密钥无效"，429 显示"太频繁" | 别把红色报错甩给用户 |
| **④ 明确的"重新生成"** | 保留上一轮的 messages 快照 | 用户不满意能重来 |

## 六、界面怎么做（先知道有这条路）

你迟早要给它做个界面。三条路：

| 方案 | 学习成本 | 适合 | 你什么时候用 |
|---|---|---|---|
| **命令行** | 0 | 验证逻辑 | 现在 |
| **Streamlit** | ⭐ 极低 | 快速做原型、内部工具 | **M2 项目、M7** |
| **FastAPI + 前端** | ⭐⭐⭐⭐ | 正式产品 | 暂时不用 |

Streamlit 的全部代码大概长这样：

```python
import streamlit as st

st.title("小助")
if "messages" not in st.session_state:
    st.session_state.messages = []

for m in st.session_state.messages:
    st.chat_message(m["role"]).write(m["content"])

if prompt := st.chat_input("说点什么"):
    st.session_state.messages.append({"role": "user", "content": prompt})
    st.chat_message("user").write(prompt)
    # ……调模型，显示回答，追加到 messages
```

**六行代码就有聊天界面了。** 这就是为什么选它。M2 项目会带你完整做一遍。

## 【常见误解】

**误解 1："它记住我了，说明它有记忆功能。"**
不。是前端每次把历史重发了。你换个浏览器、清空缓存，它立刻"失忆"。**这是产品设计，不是模型能力。**

**误解 2："上下文窗口越大越好，那我全塞进去。"**
错。窗口大不等于该塞满：**越长的上下文越贵、越慢，而且模型在超长上下文里会"注意力涣散"**（中间的内容容易被忽略，业内叫"lost in the middle"）。**精准给 3 段，胜过塞 300 段。**

**误解 3："流式输出让模型变快了。"**
不。总耗时一样，甚至略长（多了网络分片开销）。**变快的是"感知速度"。**

**误解 4："多轮对话就是把历史拼起来，很简单。"**
拼起来是简单的，**难的是"拼多少"和"怎么拼"**。截断策略、摘要、顺序、角色标注，每一个都会影响效果。这正是"应用工程"和"调通 API"的区别。
