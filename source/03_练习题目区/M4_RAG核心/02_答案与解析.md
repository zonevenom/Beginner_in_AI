## 第 1 题 · 三选一

| # | 选择 | 理由 |
|---|---|---|
| 1 | **RAG** | 知识型问答，内容会变，且**需要出处**（员工手册答错了要担责） |
| 2 | **微调** | 这是"风格/格式"问题，不是"知识"问题。RAG 改不了文风 |
| 3 | **长上下文** | 一次性分析一份长文档，不需要反复查。塞进去最直接 |
| 4 | **RAG** | 知识会变，微调每次改政策都要重训，代价太大 |
| 5 | **RAG 为主** | 3000 个报错码是"查表"，不是"学规律"。用检索最合适；如果还要固定输出格式，可以 RAG + 少量微调 |

### 附加问：为什么微调不能"灌知识"

因为**模型不是数据库，它是"接话机器"**。

微调做的事是：**调整它接话的偏好**（语气、格式、句式），而不是**往它脑子里塞一份可检索的文件**。

具体三个原因：

1. **记不牢**：微调后它可能"大致记得"，但细节（数字、日期、条款号）极易出错，而且**错得理直气壮**。
2. **改不动**：政策改一条，你得重新训一遍；RAG 只要替换那一页 PDF。
3. **没法溯源**：微调后的回答没有出处，用户无法验证。

> 行业共识：**微调学"怎么说"，RAG 学"说什么"。**

### 常见错误

- ❌ 第 3 题选 RAG。**单份文档一次性分析，RAG 是杀鸡用牛刀**（还要建库、检索，多此一举）。
- ❌ 认为"微调更高级所以更好"。**选错方案比用错参数损失大 10 倍。**

## 第 2 题 · 切分与成本

### 第 1 问：多少块

关键是**步进 = chunk_size - overlap = 500 - 50 = 450**。

```
块数 = ceil((总长 - overlap) / 步进)
     = ceil((10000 - 50) / 450)
     = ceil(9950 / 450)
     = ceil(22.1)
     = 23 块
```

**为什么不是 10000/500 = 20 块**：因为有重叠，每块只"前进"450 字，需要更多块才能覆盖全文。

### 第 2 问：每次塞多少字

```
top_k=3 × 500 字/块 = 1500 字
```

再加上提示词模板（约 200 字）和问题。粗估 **1700~1800 字**，约 **2000~2500 token**。

### 第 3 问：改成 200/20

```
步进 = 180
块数 = ceil((10000 - 20) / 180) = ceil(55.4) = 56 块
```

**影响**：

| 方面 | 变化 |
|---|---|
| 检索精度 | **提升**（每块更聚焦，噪声少） |
| 上下文完整性 | **下降**（可能切断了跨句的逻辑） |
| 块数量 | 23 → 56，索引变大 |
| 每次问答成本 | 变化不大（还是 top-3 × 200 = 600 字），**反而更省** |
| 主要风险 | **"半句话"问题**：检索到的块信息不完整，模型答不出 |

> 所以不是"越小越好"，而是"**小到刚好能表达一个完整意思**"。

### 第 4 问：overlap=400

```
步进 = 500 - 400 = 100
块数 = ceil((10000 - 400) / 100) = 96 块
```

**后果**：

1. **索引膨胀**：96 块 vs 23 块，存储和嵌入成本翻 4 倍
2. **检索结果高度重复**：top-3 可能是"几乎一样的三段"，等于只拿到 1 段有效信息
3. **浪费 token**：同样的内容被塞了三遍

> **经验上限：overlap 不要超过 chunk_size 的 30%。**

### 常见错误

- ❌ 用 `10000/500`。**忘了重叠。**
- ✅ 高分答案会指出"小块更省 token 但更容易断句"这种权衡关系。

## 第 3 题 · 补全提示词与引用

### 第 1 问：四条规则

```
1. 只能使用资料中的信息，不要使用你自己的知识。
2. 每个结论后面用 [编号] 标注来源，例如 [1]。
3. 如果资料里没有足够信息，直接回答"根据现有资料无法回答"，不要猜测。
4. 回答简洁，不超过 200 字。
```

### 第 2 问：`build_context`

```python
def build_context(hits):
    """
    hits: [{"text": ..., "source": "a.pdf", "page": 3}, ...]
    返回 (context 字符串, refs 字典)
    """
    lines = []
    refs = {}
    for i, h in enumerate(hits, start=1):
        tag = f"[{i}]"
        lines.append(f"{tag} {h['text']}")
        refs[tag] = f"{h['source']} 第 {h.get('page', '?')} 页"

    context = "\n\n".join(lines)
    return context, refs
```

**注意 `enumerate(hits, start=1)`**：编号从 1 开始，和提示词里的 `[1]` 对齐。用默认的 0 会导致**引用整体错位一位**——这是最隐蔽的 bug。

### 第 3 问：资料里没有时

希望模型输出：**"根据现有资料无法回答。"**（明确、简短、不编）

提示词里要保证这一点，必须做到三件事：

1. **明确写出来**这句话的模板（"直接回答'根据现有资料无法回答'"），而不是含糊地说"不要编造"
2. **在规则里排到前面**（位置越靠前权重越高）
3. **不要在同一段里写"请尽量回答"**（自相矛盾，模型会选后者）

```python
# 反面示例（自相矛盾）
"如果资料里没有，就说不知道，但请尽量给出有用的回答。"   # ❌ 它一定会编
```

### 常见错误

- ❌ 编号从 0 开始。
- ❌ 规则写"不要编造"但不给具体句式。**模型需要一个"照抄的句子"。**

## 第 4 题 · 四个症状，四个病因

| # | 病因 | 第一步排查 |
|---|---|---|
| **A** | **检索没找到**（环节 ④），或切分把答案切碎了（环节 ②） | **打印检索到的 top-5 原文**。如果里面没有那段话 → 检索问题；如果有但排名靠后 → 调 top-k 或加混合检索 |
| **B** | **引用映射错**（环节 ⑤ 的元数据） | 检查 `refs` 的编号是否从 1 开始、`hits` 顺序是否在排序后被改动过 |
| **C** | **top-k 太大 / 没加阈值**（环节 ④） | 把 k 从 10 降到 3，加相似度阈值 |
| **D** | **模型没遵守"只用资料"**（环节 ⑤ 提示词） | 检查提示词有没有"只能使用资料"；检查 temperature 是否过高；检查资料里的原文是否真的写的是 3-5（也可能**资料本身**就是 30） |

### 第 D 题的关键点

**先确认"资料里到底写的是几"。**

如果检索到的原文就是"30 个工作日"，那模型没错，**是你的知识库过时了**。
如果原文是"3-5"，模型说"30"，那是模型在改数字——**这种情况要降低 temperature，并加"数字必须与原文完全一致"的规则**。

> 这题的考点：**"模型答错"和"资料错了"是两回事，先看原文。** 这是 RAG 调试第一铁律的实践。

## 第 5 题 · 为什么"说不知道"是优点

### 参考答案：不同意那个说法

**从用户体验看**：

一个总在编造的 RAG，用户第一次被骗会愤怒，第二次就不用了。
一个会说"资料里没有"的 RAG，用户会知道"这个系统靠谱，它不知道就是真没有"，然后**换个问法或去问人**。

> **可信度比覆盖率值钱。** 客服场景里，一句错误的"退款 30 天"可能导致投诉；一句"我查不到，帮您转人工"只是多一步。

**从工程可维护性看**：

- "说不知道"是**可观测的信号**：你知道哪些问题覆盖不到，可以针对性补文档
- 一直硬答的系统，你**永远不知道它错了多少**（错误被隐藏了）

**具体场景**：

> 医院导诊机器人。用户问"吃了这个药能不能喝酒"。
> - 编造型：给出一个看似合理的答案 → 可能出人命
> - 拒答型："这个问题超出我的知识范围，请咨询医生" → 正确

### 但要加一个限定条件

**"经常说不知道"确实说明系统有问题**——说明你的知识库覆盖不够，或者检索没做好。

所以正确的判断是：

| 指标 | 健康值 |
|---|---|
| 该答的**答对率** | 高 |
| 不该答的**拒答率** | 高 |
| **整体拒答率** | 应该**低**（否则说明库不全） |

> **理想状态：该答的都答对，不该答的都拒掉。** 两个指标要一起看，只看一个都会骗人。

## 第 6 题 · 做一个最小 RAG

### 参考实现骨架

```python
# loader.py
from pypdf import PdfReader

def load_pdf(path):
    reader = PdfReader(path)
    pages = []
    for i, page in enumerate(reader.pages, start=1):
        text = page.extract_text() or ""
        pages.append({"page": i, "text": text})
    return pages
```

```python
# splitter.py
import re

def clean(text):
    text = re.sub(r"\n{3,}", "\n\n", text)      # 多余空行
    text = re.sub(r"(?<!\n)\n(?!\n)", "", text)  # 单换行（PDF 断行）直接删
    text = re.sub(r"[ \t]{2,}", " ", text)
    return text.strip()

def split(text, doc_name, chunk_size=500, overlap=50):
    out, start, idx = [], 0, 0
    while start < len(text):
        piece = text[start:start + chunk_size]
        if piece.strip():
            out.append({
                "id": f"{doc_name}_{idx}",
                "text": piece,
                "source": doc_name,
                "page": None,          # 需要按页切时再填
                "chunk_index": idx,
            })
            idx += 1
        start += chunk_size - overlap
    return out
```

**注意 `page: None`**：这是本题的一个真实难点——**按页切分和按长度切分是冲突的**。

两种解法：
1. **按页切**（每页单独切），页码天然保留，但页尾页首会被割裂
2. **整本切**，然后根据字符偏移量估算页码（不精确）

> 建议：**先按页切**。页码准确比语义连贯更重要——因为用户要的是"我能去第 3 页核对"。

### 参考评测结果（示例）

| # | 问题 | 检索对? | 回答对? | 引用对? |
|---|---|---|---|---|
| 1 | 简单事实 | ✅ | ✅ | ✅ |
| 2 | 跨两页 | ⚠️ 只找到一半 | ❌ | ✅ |
| 3 | 同义改写 | ✅ | ✅ | ✅ |
| 4 | 文档没有 | ✅（正确返回无关块） | ✅ 拒答 | — |
| 5 | 需计算 | ✅ | ❌ 算错 | ✅ |

**结论**：检索 4.5/5，回答 3/5，引用 4/5。

**这告诉你什么**：你的瓶颈**不在检索，在生成和计算**。
- 跨页问题 → 加"父子块"或增大 chunk_size
- 计算问题 → 这不是 RAG 的活，**该上工具调用（M6）**

> 能做出这种归因，你就已经跨过了"调通 API"的门槛。
