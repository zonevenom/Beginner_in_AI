## 第 1 题 · 看体检表开药方

### 参考答案

| 组 | 诊断 | 先改什么 |
|---|---|---|
| **A** | Recall 高、Precision 极低 → **噪声病** | 加阈值、减小 k、**加重排**。别动切分 |
| **B** | Recall 低、Precision 高 → **漏召回病** | 加大 k、**混合检索**（精确词问题）、父子块 |
| **C** | 检索完美、答对率低 → **生成层病** | 改提示词（"只用资料"）、降到 temperature=0.1、缩短 context |
| **D** | 全面崩、拒答 0 → **地基烂** | **先修数据和切分**，其他都别动 |

### 第 D 组的深意

**"拒答正确率 0.00"意味着：该拒答的题，它一次都没拒。**

这说明你的阈值形同虚设，或者提示词里**根本没有"允许说不知道"这条规则**。

一条 RAG 从不说"不知道"，是**最危险**的状态——因为它对任何问题都会给一个看似合理的答案。

> 排查顺序：先看阈值是不是设成了 0，再看提示词有没有拒答模板，最后才怀疑检索。

### 常见错误

- ❌ A 组去调 chunk_size。**Recall 已经 0.9 了，说明找得到，问题在"给太多"。**
- ✅ 高分答案会指出：**A 组先加重排而不是先减 k**，因为减 k 会掉 Recall。

## 第 2 题 · 算两个指标

### 第 1 问：Recall@5

gold 是 `p3_c1`，在返回列表第 3 位 → **命中**。

```
Recall@5 = 1（这题命中了）
```

如果算 20 题的平均，就是"命中题数 / 20"。

### 第 2 问：Precision@3

前 3 条：`p3_c0, p5_c2, p3_c1`

相关的只有 `p3_c1`（1 条）。

```
Precision@3 = 1/3 ≈ 0.33
```

### 第 3 问：Precision@5

5 条里相关的是 `p3_c1` 和 `p3_c1_dup`（2 条）。

```
Precision@5 = 2/5 = 0.40
```

### 第 4 问：Recall@1

top-1 是 `p3_c0`，不含 gold。

```
Recall@1 = 0（这题没命中）
```

### 第 5 问：重复块

**怎么产生的**：

1. **overlap 太大**（500/400），相邻块内容高度重叠
2. 同一段文字在 PDF 里出现两次（如摘要 + 正文重复）
3. 父子块方案里，父块和子块被同时召回

**影响**：

| 方面 | 影响 |
|---|---|
| Precision | **被拉低**（重复的不算新信息，但占名额） |
| Recall | 不变（该在的还在） |
| 模型 | **有害**：同一个信息出现三遍，模型可能误以为"这很重要"，或直接抄三遍 |
| 成本 | 浪费 token |

**修法**：召回后按 `page + 文本前缀` 做去重；控制 overlap ≤ chunk_size 的 30%。

> 这题的设计意图：**让你意识到"Precision 低"不一定是"检索不准"，也可能只是"重复太多"。**

## 第 3 题 · 实现 RRF

### 第 1 问：手算（k=60）

```
score = 1/(60+rank)
```

**向量列表**：

| 文档 | rank | 得分 |
|---|---|---|
| a | 1 | 1/61 = 0.016393 |
| b | 2 | 1/62 = 0.016129 |
| c | 3 | 1/63 = 0.015873 |
| d | 4 | 1/64 = 0.015625 |
| e | 5 | 1/65 = 0.015385 |

**BM25 列表**：

| 文档 | rank | 得分 |
|---|---|---|
| c | 1 | 1/61 = 0.016393 |
| a | 2 | 1/62 = 0.016129 |
| f | 3 | 1/63 = 0.015873 |
| b | 4 | 1/64 = 0.015625 |
| g | 5 | 1/65 = 0.015385 |

**合并**：

| 文档 | 总分 |
|---|---|
| **a** | 0.016393 + 0.016129 = **0.032522** |
| **c** | 0.015873 + 0.016393 = **0.032266** |
| **b** | 0.016129 + 0.015625 = **0.031754** |
| f | 0.015873 |
| d | 0.015625 |
| e, g | 0.015385 |

**前 3 名**：`a`、`c`、`b`

> 注意：`a` 在两个列表里都排第 1/第 2，所以总分最高。**RRF 天然优待"两个检索器都认可"的文档**——这正是我们想要的。

### 第 2 问：代码

```python
def rrf(*rank_lists, k=60):
    score = {}
    for ids in rank_lists:
        for rank, doc_id in enumerate(ids, start=1):
            score[doc_id] = score.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(score.items(), key=lambda x: -x[1])


print(rrf(vec_ids, bm25_ids)[:3])
# [('a', 0.03252...), ('c', 0.03226...), ('b', 0.03175...)]
```

**`*rank_lists`** 是可变形参，这样以后加第三个检索器（比如按时间排序）不用改函数。

### 第 3 问：分数直接相加会怎样

假设：
- 向量分：`a=0.82`，`c=0.79`
- BM25 分：`c=18.5`，`a=3.2`

**直接相加**：

```
a = 0.82 + 3.2  = 4.02
c = 0.79 + 18.5 = 19.29   ← c 完胜
```

**RRF**：

```
a = 1/61 + 1/62 = 0.0325
c = 1/63 + 1/61 = 0.0323   ← a 略胜
```

**问题在哪**：BM25 的量纲是 0~几十，向量是 0~1。**直接相加等于"BM25 说了算"，向量检索形同虚设。**

有人会说"那我归一化再相加"。但归一化需要知道分布，而且**不同查询的分布还不一样**，很难做对。

> **RRF 用排名绕过了这个问题：不管你的分数是 0.8 还是 18.5，我只关心你排第几。**
> 这就是"排名比分数更稳"的工程智慧。

### 常见错误

- ❌ `k` 取 0 或 1。**会导致除零或排名差距过大**，第一名 1.0，第二名 0.5，太陡。
- ❌ 忘记 `start=1`，用 0 开始。

## 第 4 题 · 多查询改写

### 第 1 问：`multi_query`

```python
def multi_query(q, client, model="deepseek-chat"):
    resp = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": REWRITE_PROMPT.format(q=q)}],
        temperature=0.7,      # 这里要一点发散，才能改出不同说法
    )
    raw = resp.choices[0].message.content

    lines = [l.strip(" -•\t") for l in raw.splitlines() if l.strip()]
    out = []
    for line in [q] + lines:
        if line and line not in out:
            out.append(line)
    return out[:4]
```

**两个细节**：

- `temperature=0.7`：改写任务**需要发散**，和事实问答相反。
- `if line not in out`：去重。**同一个说法检索两次是纯浪费。**

### 第 2 问：`search_multi`

```python
def search_multi(queries, retrieve_fn, k=5):
    merged = {}
    for qi, q in enumerate(queries):
        for rank, hit in enumerate(retrieve_fn(q, k), start=1):
            cid = hit["id"]
            if cid not in merged:
                merged[cid] = {"hit": hit, "rrf": 0.0, "best_score": 0.0}
            merged[cid]["rrf"] += 1.0 / (60 + rank)
            merged[cid]["best_score"] = max(merged[cid]["best_score"], hit["score"])

    return sorted(merged.values(), key=lambda x: -x["rrf"])
```

### 第 3 问：同一 chunk 被多次命中，分数怎么算

**方案 A：RRF 累加（推荐）**

同一块被 3 个查询命中，得 3 份分。**"被越多查询命中"= 越可能是真的好。**

```python
merged[cid]["rrf"] += 1.0 / (60 + rank)
```

**方案 B：取最高相似度**

```python
merged[cid]["best_score"] = max(...)
```

**什么时候用 B**：当你发现"累加"会让一些"用词模糊但广泛相关"的块排到前面时。

> **我的建议：主排序用 RRF 累加，平局时用 best_score 决。** 两个都留着，方便调试。

### 第 4 问：成本

| 项 | 基线 | 多查询 |
|---|---|---|
| 改写调用 | 0 | 1 次（贵，是聊天模型） |
| embedding 调用 | 1 次 | 4 次（便宜） |
| 检索计算 | 1 次 | 4 次（几乎免费） |

**总成本约 2~2.5 倍**（改写那一次相对贵）。

**值不值？** 取决于场景：

- 用户问题**说法多样**、文档**用词固定**（如法律、医疗）→ **很值**
- 用户问题和文档用词本来就一致 → 不值
- 有延迟要求（<1 秒）→ 不值（改写要多几百毫秒）

> 这就是"工程判断"：**同一个技术，在不同场景下价值不同。** 面试时能说出这句话，比会写代码更值钱。

## 第 5 题 · 加了重排反而变差

### 至少 3 个原因 + 验证方法

| # | 原因 | 怎么验证 |
|---|---|---|
| 1 | **候选集太小**（top-30 里压根没有 gold） | 算 `Recall@30`。如果只有 0.6，那重排再准也没用——**先扩候选** |
| 2 | **分数方向反了**（把最低分当最高分） | 打印前 5 条的 rerank 分数，看是否和"人工判断的相关性"同向 |
| 3 | **rerank 模型不适合中文/领域** | 换一个中文模型对比；或人工看"它把 gold 排第几" |
| 4 | **重排后取 top-3 太激进** | 试 top-5；对比答对率 |
| 5 | **重排把"长块"惩罚了** | 看被降权的块是否长度异常（有的模型偏爱短文本） |
| 6 | **模型被"看起来相关但没答案"的块骗了** | 这是 rerank 的本质局限：它判断"相关性"，不判断"是否包含答案" |

### 第 6 条最值得展开

**Rerank 模型的训练目标是"相关性"，不是"可回答性"。**

一个块可能大谈"退款政策的重要性"（高度相关），但**不含"几天到账"这个具体答案**。
一个块可能是"退款 3-5 个工作日到账"（直接答案），但语义上和问题只是"中等相关"。

**于是 rerank 把前者排到前面，答对率反而下降。**

> 这是 RAG 里一个很深的坑：**"相关"≠"有用"**。
> 解法：用带答案标注的数据微调 rerank 模型（超出你的范围），或者**同时保留向量排序和 rerank 排序，做加权融合**。

### 常见错误

- ❌ 只说"重排模型不好"。**先排除候选集太小这个最常见的低级原因。**

## 第 6 题 · 做出你的第一个"优化前后对比"

### 参考产出

**基线（chunk=500, k=3, 阈值 0.5）**

| 指标 | 值 |
|---|---|
| Recall@5 | 0.70（14/20） |
| Precision@3 | 0.42 |
| 答对率 | 0.60（12/20） |
| 拒答正确率 | 0.50（1/2） |

**优化：chunk_size 500 → 300**

| 指标 | 值 | 变化 |
|---|---|---|
| Recall@5 | 0.80 | +10pt |
| Precision@3 | 0.51 | +9pt |
| 答对率 | 0.55 | **-5pt** |
| 拒答正确率 | 0.50 | 不变 |

**结论（100 字）**：

> 切小到 300 后，Recall 从 0.70 提到 0.80，因为短块语义更聚焦，"退款到账"这种具体问题更容易命中。但答对率掉了 5 个点：跨页题（4 题）里有 2 题因为答案被切断而答错。**说明 300 对这个文档"太碎"**，下一步应该试"小块检索 + 父子块扩展"，而不是继续调小。

### 这段结论为什么好

1. 有**具体数字**，不是"变好了"
2. 有**归因**（"因为短块更聚焦"）
3. 承认了**副作用**（答对率下降、跨页题变差）
4. 给出了**下一步方案**（父子块，而不是继续调参）

> 这就是"工程思维"和"调参碰运气"的区别。
> 面试官听到第 3、4 点，会立刻知道你**真的做过**，不是背的。
