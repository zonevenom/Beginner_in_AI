## 第 1 题 · 三种死穴

### 第 1 问：分别属于哪种

| # | 类型 | 说明 |
|---|---|---|
| 1 | **表述不同**（近义但字面不同） | "请假怎么请" vs "休假申请流程"，没有共同的关键词 |
| 2 | **跨语言** | 中文库、英文查询，字面零重叠 |
| 3 | **同义词 / 口语 vs 书面语** | "加班" vs "延时工作"，"补贴" vs "补偿" |

> 严格说，1 和 3 都属于"词汇不匹配（vocabulary mismatch）"。分三类是为了让你记住**触发条件是"字面不同"**。

### 第 2 问：语义检索为什么能搜到

因为 embedding 是在**大量真实语料**上学的，它见过：

- "请假"和"休假"经常出现在同一类句子里
- "refund"和"退款"在中英对照语料里是邻居
- "加班补贴"和"延时工作补偿"是同一个概念的不同说法

所以它们的**坐标很近**，即使一个字都不重合。

> 关键认知：**语义检索不看你用了什么词，只看你的意思落在哪。**

### 第 3 问：一个语义检索也会失败的制度类查询

**参考答案**：

> 搜"年假有多少天"。

失败原因：制度里可能有一张**表格**（"工龄 1-3 年：5 天；3-10 年：10 天"），表格在向量化时会被压成一段文字，**"你的工龄"这个条件被丢了**。向量只捕捉了"年假、天数"的语义，无法做"按我的工龄查表"这种**条件计算**。

其他好答案：

- "报销标准是每小时多少钱"——需要**数值精确匹配**，向量不擅长
- "第 3.2 条说的是什么"——需要**精确定位条款编号**，关键词更准

> 这题想让你明白：**语义检索解决"表述不同"，不解决"计算"和"精确定位"。** 后者要靠结构化查询或工具调用（M6）。

## 第 2 题 · 手算余弦相似度

### 第 1 问：三个值

公式：`cos = (A·B) / (|A| × |B|)`

**① A=[1,0]，B=[1,1]**

```
A·B = 1×1 + 0×1 = 1
|A| = 1，|B| = √2 ≈ 1.414
cos = 1 / 1.414 ≈ 0.71
```

**② A=[1,0]，B=[-1,0]**

```
A·B = -1
|A| = 1，|B| = 1
cos = -1 / 1 = -1.00
```

**③ A=[1,2]，B=[2,4]**

```
A·B = 2 + 8 = 10
|A| = √5 ≈ 2.236，|B| = √20 ≈ 4.472
cos = 10 / (2.236 × 4.472) = 10 / 10 = 1.00
```

### 第 2 问：为什么 ③ 是 1

因为 `[2,4] = 2 × [1,2]`，**两个向量方向完全相同，只是长度差 2 倍**。

而余弦只看夹角，不看长度。

> **结论：余弦相似度衡量的是"方向是否一致"，不是"距离有多近"。**

这也解释了为什么短句和长段落说同一件事时，余弦相似度依然很高——这正是我们想要的行为。

### 第 3 问：归一化后还能用点积吗

**能。而且必须用。**

推导（一行）：

```
cos(A,B) = (A·B) / (|A||B|)
若 |A| = |B| = 1，则 cos(A,B) = A·B
```

所以工程上标准做法是：

1. 入库前把每条向量归一化
2. 查询时把查询向量也归一化
3. 直接用点积（矩阵乘法）批量算，**一次算 100 万条也只要毫秒级**

```python
# 归一化后，批量相似度就是一次矩阵乘法
scores = matrix @ query_vec      # matrix: (N, d), query_vec: (d,) → (N,)
```

> 这就是"为什么所有向量库都默认归一化"的原因：**不只是数值稳定，更是为了能用矩阵乘法提速。**

### 常见错误

- ❌ ② 算成 0。**方向相反是 -1，不是 0**；垂直才是 0。
- ❌ ③ 看到长度不同就以为相似度低。**这是最典型的直觉错误。**

## 第 3 题 · 最小语义搜索

### 参考实现

```python
import json
import os

import numpy as np
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()

# 以你实际选用的厂商为准：这里用"OpenAI 兼容"的写法
client = OpenAI(
    api_key=os.getenv("EMBED_API_KEY"),
    base_url=os.getenv("EMBED_BASE_URL", "https://api.example.com/v1"),
)
EMBED_MODEL = os.getenv("EMBED_MODEL", "embedding-3")

TEXTS = [
    "这款保温杯 500ml，能保温 12 小时",
    "无线鼠标，静音按键，适合办公",
    "纯棉 T 恤，透气吸汗，夏天穿很舒服",
    "充电宝 10000mAh，支持快充",
    "笔记本支架，铝合金，可调节高度",
    "蓝牙耳机，降噪，续航 30 小时",
]

THRESHOLD = 0.5


def embed_batch(texts):
    """一次性批量拿向量。"""
    resp = client.embeddings.create(model=EMBED_MODEL, input=texts)
    return [np.array(d.embedding, dtype=np.float32) for d in resp.data]


def normalize(v):
    return v / (np.linalg.norm(v) + 1e-10)


def build_index(path="vectors.json"):
    vecs = embed_batch(TEXTS)
    data = [
        {"text": t, "vec": [float(x) for x in normalize(v)]}
        for t, v in zip(TEXTS, vecs)
    ]
    with open(path, "w", encoding="utf-8") as f:
        json.dump(data, f, ensure_ascii=False)
    return data


def load_index(path="vectors.json"):
    if not os.path.exists(path):
        return build_index(path)
    with open(path, encoding="utf-8") as f:
        data = json.load(f)
    matrix = np.array([d["vec"] for d in data], dtype=np.float32)
    return data, matrix


def search(q, data, matrix, top_k=3):
    qv = normalize(embed_batch([q])[0])
    scores = matrix @ qv                      # 归一化后，点积即余弦
    order = np.argsort(-scores)[:top_k]

    print(f"\n查询：{q}")
    hit = False
    for i in order:
        s = float(scores[i])
        if s < THRESHOLD:
            continue
        hit = True
        print(f"  {s:.4f}  {data[i]['text']}")
    if not hit:
        print("  （没有相关内容，最高分低于阈值）")


if __name__ == "__main__":
    data, matrix = load_index()
    for q in ["能保温多久", "礼物送什么好", "给手机充电用啥"]:
        search(q, data, matrix)
```

### 关键点解释

| 代码 | 为什么 |
|---|---|
| `embed_batch` 一次传列表 | 6 次请求变 1 次，快且可能更便宜 |
| `normalize` 在**存的时候**做 | 保证库里的一致；查询时也做，才能用点积 |
| `matrix @ qv` | 一次算完所有相似度，不用 for 循环 |
| `np.argsort(-scores)` | 负号 = 降序 |
| `if s < THRESHOLD: continue` | **不是 break**。break 会漏掉后面可能高分的（虽然排好序了不会，但养成 continue 的习惯更安全） |

### 常见错误

- ❌ 用 `for` 循环一个个算余弦，再 `sorted`。**能跑，但慢 100 倍，而且没机会体会矩阵乘法的好处。**
- ❌ 存的时候归一化，查的时候忘了。**分数还是对的**（因为除法抵消），但你会困惑"为什么点积能当余弦用"。
- ✅ 高分答案会把"查询文本"和"库文本"用**同一个模型**编码。**用了两个不同模型，分数完全无意义**——这是比什么都重要的铁律。

## 第 4 题 · 三个"看起来能跑但结果不对"

### 问题 A：Chroma 没传 embeddings

**原因**：Chroma 在 `add()` 时如果不给 `embeddings`，会**自动用它的默认 embedding 函数**（通常是一个内置的 ONNX 小模型，会静默下载）。

于是：库里存的是**默认模型的向量**，查询时你传的是**你自己模型的向量**。

> **两套坐标系统，混在一起比距离。** 结果就是随机排序，而且**不报错**。

**修法**：

```python
col.add(ids=ids, documents=texts, embeddings=my_vectors)   # 显式传
res = col.query(query_embeddings=[q_vec], n_results=3)     # 显式查
```

**如何验证你在踩这个坑**：

```python
n = col.count()
got = col.get(include=["embeddings"], limit=1)
print(len(got["embeddings"][0]))    # 输出的维度，应该和你的模型一致
```

维度对不上（比如你的是 1024，出来是 384）→ 中招了。

### 问题 B：换模型后旧向量没删

**原因**：不同模型的向量空间**互不兼容**。1024 维和 1536 维连矩阵乘法都做不了，直接报维度错。

即使维度碰巧相同（比如两个模型都是 1024 维），**空间也不同，分数毫无意义**。

**修法**：

1. 删除旧库/旧 json
2. 全量重算
3. **在库里记录模型名和维度**（比如 collection 名字带上 `_bge_1024`），避免以后混用

> 这是工程上的重要习惯：**向量数据必须和"生成它的模型"绑定。** 换模型 = 全量重建，没有捷径。

### 问题 C：没归一化导致短句分数偏低

**原因**：这题是个"陷阱题"——**如果用的是余弦相似度，归一化与否结果相同**（除法会抵消）。

真正会导致"短句分数偏低"的原因通常是：

1. 你用的是**点积**或**欧氏距离**，而不是余弦
2. 长段落里混进了大量无关内容，**把语义"稀释"了**（这是真的，不是归一化的问题）

**修法**：

- 统一用余弦（或先归一化再用点积）
- 对长文本做**切分**（chunk），别把一整段塞成一个向量 —— **这正是 M4 要讲的**
- 给标题/关键句更高权重（M5 的混合检索）

> 这题的设计意图：**让你学会区分"归一化问题"和"长文本稀释问题"。** 它们的症状像，病因完全不同。

### 常见错误

- ❌ 认为 A 会报错。**它不报错，这才是最坑的。**
- ✅ 高分答案会提出"给 collection 名字加模型标识"这种工程习惯。

## 第 5 题 · 该用哪种检索

| # | 查询 | 选择 | 理由 |
|---|---|---|---|
| 1 | 订单号 `A20240315001` | **关键词** | 精确标识符，向量会把它当"一串文本"，召回一堆别的订单 |
| 2 | "东西坏了怎么办" | **语义** | 口语化，和文档里"质量问题处理"字面完全不同 |
| 3 | 报错 `ERR_CONN_RESET` | **关键词** | 错误码是精确字符串，必须原样匹配 |
| 4 | "怎么取消自动续费" | **语义**（+关键词兜底） | 概念查询，但"自动续费"本身也可能是关键词，混合更稳 |
| 5 | 找提到"张伟"的记录 | **关键词** | 人名需要精确匹配。"张伟"和"张玮"在向量空间极近，会互相污染 |
| 6 | "上次说的那个关于预算的事儿" | **语义** | 模糊指代，关键词完全无能 |

### 判断口诀

> **"能一字不差打出来的" → 关键词；"只能描述出意思的" → 语义。**

再加一条工程经验：**只要你的系统里同时有"编号/代码/人名/错误码"，就必须做混合检索**，不能只上向量。这就是 M5 的第一课。

## 第 6 题 · 给你的笔记做语义搜索

### 参考产出

| 查询 | 期望命中 | top-1 内容 | top-1 分数 | 符合预期 |
|---|---|---|---|---|
| 同义改写："怎么把钱要回来" | "退款流程说明" | 退款流程说明 | 0.78 | ✅ |
| 同义改写："电脑好卡" | "清理后台程序释放内存" | 清理后台程序… | 0.72 | ✅ |
| 跨表述："想换个活法" | "职业转型的三个阶段" | 职业转型… | 0.65 | ✅ |
| 跨表述："东西送到一半不动了" | "物流停滞处理办法" | 物流停滞… | 0.74 | ✅ |
| **库里没有："怎么给猫剪指甲"** | **无** | 宠物用品采购清单 | **0.42** | ✅（低于阈值，正确拒绝） |

### 关键观察

第 5 个查询的 top-1 是 **0.42**。如果你把阈值设成 0.5，系统会正确地说"没找到"。
如果阈值是 0.3，它就会把"宠物用品采购清单"糊到你脸上。

> **这就是阈值的全部意义：它是"敢不敢说不知道"的开关。**

### 加分题：阈值扫描的方法

```python
for th in [0.3, 0.4, 0.5, 0.6, 0.7, 0.8, 0.9]:
    tp = fp = fn = 0
    for q, expect in LABELED_QUERIES:      # 你人工标注好的"该不该命中"
        got = search(q, ...)               # 返回是否命中
        if expect and got: tp += 1
        elif not expect and got: fp += 1
        elif expect and not got: fn += 1
    print(th, "误召回", fp, "漏召回", fn)
```

**你会看到一条典型曲线**：阈值低 → 误召回多；阈值高 → 漏召回多。中间有个"甜点"。

> 这个"找甜点"的动作，就是 M5 里"评估驱动优化"的雏形。你现在已经在做评测了。

### 常见错误

- ❌ 5 个查询全是"库里明显有的"。**那样测不出系统的边界。**
- ✅ 高分答案会保留"不相关查询"的分数，作为将来定阈值的依据。
