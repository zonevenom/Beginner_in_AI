## 第 1 题 · 该部署到哪

| # | 选择 | 理由 |
|---|---|---|
| 1 | **内网穿透** | 今晚就要，零配置。缺点（地址会变、电脑要开着）在这个场景不重要 |
| 2 | **Streamlit Cloud（或国内云）** | 要"长期活着 + 点开就能用"。Cloud 免费且稳定；如果面向国内用户、要更稳，选国内云 |
| 3 | **HF Spaces** | 海外访问快，AI 社区习惯在这看 demo |
| 4 | **内网服务器** | 不能上公网 → 只能在公司内网跑，或用 Docker 部署到内网机器 |

### 判断口诀

> **"给谁看、看多久、在哪看"** —— 三个问题定方案。

- 给谁：自己/朋友 → 临时；招聘方 → 稳定；海外 → HF
- 看多久：5 分钟 → 穿透；3 个月 → Cloud；长期 → 云服务器
- 在哪：公网 / 内网 / 海外

### 常见错误

- ❌ 第 1 题选 Cloud。**部署 Cloud 要推 GitHub、等构建，20 分钟起步**，而穿透 1 分钟。**场景决定方案，不是"越正式越好"。**

## 第 2 题 · 补全接口

### 第 1 问：补全

```python
@app.post("/ask")
def ask(req: AskRequest):
    if not req.question.strip():                                  # ①
        raise HTTPException(status_code=400, detail="问题不能为空")
    if len(req.question) > 500:                                   # ②
        raise HTTPException(status_code=400, detail="问题不能超过 500 字")
    if not (1 <= req.top_k <= 5):                                 # ③
        raise HTTPException(status_code=400, detail="top_k 必须在 1~5 之间")

    answer, sources = do_rag(req.question, req.top_k)             # ④
    return {"answer": answer, "sources": sources}
```

### 第 2 问：`/health` 的作用

```python
@app.get("/health")
def health():
    return {"status": "ok"}
```

三个用途：

| 用途 | 说明 |
|---|---|
| **存活探测** | 云平台/负载均衡定期访问它，返回 200 就认为服务活着 |
| **部署验证** | 部署完先访问 `/health`，能通说明"服务和路由都对"，再去测业务接口 |
| **快速定位** | 业务接口 500 时，先访问 `/health`：通了 → 业务逻辑问题；不通 → 服务本身没起来 |

> **这是"排查分层"的思路**：先确认"活着"，再确认"能干活"。

### 第 3 问：防护

| 防护 | 做法 |
|---|---|
| **限流** | 每个 IP 每分钟最多 N 次（`slowapi` 库，或自己用字典记时间戳） |
| **鉴权** | 加一个 `X-API-Key` 头，只有知道 key 的人能调 |
| **输入上限** | 问题长度、`top_k` 上限（你已经做了） |
| **预算熔断** | 当天累计 token 超过阈值就返回 503 |
| **CORS 白名单** | 只允许你的前端域名调用 |

> **最低配也要做"限流 + 长度限制"。** 这两个加起来能挡住 90% 的"无意刷爆"。

## 第 3 题 · 上线后的四个"灵异事件"

### A：`ModuleNotFoundError: No module named 'pypdf'`

**原因**：`requirements.txt` 里没有 `pypdf`（或拼错了）。

**排查**：

1. 看部署平台的构建日志，找 `pip install` 那一段
2. 本地 `pip freeze | findstr pypdf` 确认版本
3. 补进 `requirements.txt`，重新部署

**根因**：**本地能跑是因为你装过，云端是全新环境。** 这是"本地 vs 云端"第一课。

> **预防**：养成习惯——只在 `requirements.txt` 里列依赖，**不在本地全局环境里随意 `pip install`**。

### B：页面能开，点发送就白屏

**原因（按概率）**：

1. **异常没被捕获**，Streamlit 把整个脚本崩了 → 页面空白
2. 前端 JS 报错（少见）
3. 无限循环导致超时

**排查**：

1. 看平台日志（Streamlit Cloud 有 "Manage app" → 日志）
2. 本地复现：`streamlit run app.py`，看终端有没有红色堆栈
3. 在白屏前的位置加 `st.write("到了这里 1")` 打点

**修法**：所有外部调用（API、文件、模型）都包 `try/except`，出错时 `st.error("...")`。

### C：用了三天突然 401

**原因**：key 失效了。三种可能：

| 可能 | 怎么确认 |
|---|---|
| **余额耗尽** | 登录平台看账单 |
| **key 被平台自动吊销**（检测到泄露） | 平台有安全通知 |
| **你换了 key 但没更新 secrets** | 对比代码和平台配置 |

**排查**：先在本地用**同一个 key** 跑一次。本地也 401 → key 的问题；本地正常 → 部署环境的配置问题（比如 secrets 名字拼错）。

### D：部署后 30 秒，本地 3 秒

**原因**：

| 原因 | 说明 |
|---|---|
| **冷启动** | 免费平台会休眠，第一个请求要唤醒容器（10~30 秒），**这是最常见原因** |
| **网络** | 云端调 API 的链路更长 |
| **资源小** | 免费版 CPU 只有 0.1~1 核 |
| **每次重建索引** | 如果你的代码在启动时重算 embedding，那每次冷启动都要重跑 |

**排查**：连续请求 3 次，看是不是只有第 1 次慢。**只有第 1 次慢 = 冷启动，这是正常现象，不是你代码的问题。**

**优化**：

- 把"建索引"改成**离线做好、直接加载文件**（P5 的 `store.load()` 就是这个思路）
- 用 `@st.cache_resource` 缓存模型/索引

```python
@st.cache_resource
def get_index():
    return load()
```

> `@st.cache_resource` 是 Streamlit 最重要的装饰器：**它让"加载索引"只做一次，而不是每次交互都做。**

## 第 4 题 · 密钥的四种写法

| # | 可以接受吗 | 理由 |
|---|---|---|
| 1 | ⚠️ **不建议，即使没推 GitHub** | 你永远不知道哪天会 `git add .`；也可能发给同事、发到群里。**"暂时没泄露"不等于"安全"** |
| 2 | ✅ **可以** | 标准做法。key 在环境里，代码里只有变量名 |
| 3 | ⚠️ **看场景** | 让用户填**自己的** key 是可以的（BYOK 模式），但要明确提示"你的 key 只存在本次会话"；**绝不能**拿它当"绕过自己成本"的手段还不告知 |
| 4 | ✅ **可以** | 平台提供的 secrets 机制，就是干这个的 |

### 附加问：不小心提交了怎么办

**第一件事：立刻去平台吊销（revoke）那个 key，重新生成。**

顺序不能反：

```
❌ 先删文件、先改 git 历史 → key 已经泄露了，删了也没用
✅ 先吊销 → 再清理仓库 → 再重新部署
```

**为什么**：GitHub 上有专门的爬虫，**提交后几分钟内**就会扫到并开始用。你的"删除提交"救不了已经泄露的 key。

吊销之后再做：

```bash
# 从 git 历史里彻底移除（需要 git-filter-repo 或 BFG）
git filter-repo --path .env --invert-paths
```

> **记住这个顺序：吊销 > 清理 > 复盘。** 先止损，再善后。

## 第 5 题 · 免费额度能撑多久

### 第 1 问：一个用户一天

```
5 次 × 1500 token = 7500 token/天
```

### 第 2 问：一个用户能用多少天

```
5,000,000 / 7500 ≈ 666.7 天 ≈ 1.8 年
```

### 第 3 问：50 个用户

```
50 × 7500 = 375,000 token/天
5,000,000 / 375,000 ≈ 13.3 天
```

**两周就没了。**

### 第 4 问：限流能延长多少

**关键：限流不减少"总次数"，只减少"并发冲击"。**

如果用户本来一天问 5 次，限流"每分钟 1 次"**不会减少总量**——只是把 5 次分散到 5 分钟。

所以：

```
延长倍数 ≈ 1（对总量几乎无影响）
```

**但如果限流是"每人每天最多 3 次"**：

```
50 × 3 × 1500 = 225,000/天
5,000,000 / 225,000 ≈ 22 天
```

**延长约 67%。**

> **这题的重点**：区分"限速（rate limit）"和"限配额（quota）"。
> - 限速：防瞬时冲击（防刷）
> - 限配额：防总量耗尽（防破产）
> **两个都要，但它们解决不同问题。**

### 第 5 问：还有什么办法

| 办法 | 省多少 | 代价 |
|---|---|---|
| **压缩 system 提示词** | 5~15% | 可能损失一点效果 |
| **减少 top_k（3→2）** | 10~20% | 可能掉召回 |
| **限制输出长度**（"不超过 100 字"） | **20~40%**（输出通常更贵） | 答案可能不够详细 |
| **缓存相同问题** | 取决于重复率，热点问题能省 50%+ | 要设计缓存键 |
| **用小模型做初筛**（简单问题不走大模型） | 20~30% | 实现复杂 |
| **前端做输入建议**（减少无效提问） | 不定 | 产品设计 |

> **最有效的是"限制输出长度"。** 因为输出 token 通常比输入贵 2~4 倍（M0 第 3 题算过）。

### 加分题：找不懂技术的人试用

**你会观察到的事**：

| 现象 | 说明什么 |
|---|---|
| 他不知道能问什么 | 你的界面缺"示例问题" |
| 他问了一个你文档里没有的问题，看到"无法回答"就以为坏了 | 你的拒答提示太生硬，应该加"你可以试试问：..." |
| 他连续问了 3 个几乎一样的问题 | 你的第一次回答没解决他的问题 |
| 他说"这跟 ChatGPT 有什么区别" | **这是最致命的问题**——说明你的价值没说清 |

> 最后一条最重要。**如果你的 RAG 和直接问 ChatGPT 没区别，那你的项目就没有存在理由。**
> 差异点应该是：**你的文档、你的出处、你的时效性。**
