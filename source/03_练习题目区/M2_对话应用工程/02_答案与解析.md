## 第 1 题 · 画出第 3 轮的消息数组

### 第 1 问：完整数组

```python
[
  {"role": "system",    "content": "你叫小助，说话简短。"},
  {"role": "user",      "content": "我叫张三"},
  {"role": "assistant", "content": "你好张三"},
  {"role": "user",      "content": "我在做电商"},
  {"role": "assistant", "content": "好的，电商很有前景"},
  {"role": "user",      "content": "我叫什么？"},
]
```

**关键点**：`system` 在最前，然后**严格按时间顺序**一问一答交替，最后一条是当前问题。

### 第 2 问：只发最后一句

它**必然答"我不知道你的名字"**，或者**编一个**。

因为模型无状态，它只看到"我叫什么？"这七个字。**没有前文，这个问题本身是没法回答的**——它只能瞎猜（这就是幻觉的来源之一）。

### 第 3 问：漏存第 2 轮助手的回答

数组会变成：

```
system / user:我叫张三 / assistant:你好张三 / user:我在做电商 / user:我叫什么？
```

出现**两个连续的 user**。后果：

- 模型会困惑"这两句是同一个人连说的吗"
- 它可能认为"我在做电商"和"我叫什么"是**同一个问题的一部分**
- 更常见的：它回答时**不知道自己刚才说过"电商很有前景"**，可能重复说一遍，前后矛盾

> **规则：一问一答必须成对出现。** 这就是为什么第 4 题要特别处理"奇数条"的情况。

### 常见错误

- ❌ 把 `system` 放到最后。**位置影响权重**，放后面它可能盖过用户的话。
- ❌ 认为"反正模型会自己拼上文"。**不会，它只能看到你发过去的东西。**

## 第 2 题 · 补全两行

### 答案

```python
    # ① 缺这行
    messages.append({"role": "user", "content": q})

    ...

    # ② 缺这行
    messages.append({"role": "assistant", "content": answer})
```

### 漏了 ② 会发生什么（真实例子）

**现象 1：自问自答。**
你说"讲个笑话"，它讲了。你说"再来一个"，它答"好的，还是刚才那个：……"——因为它不知道自己已经讲过一个了。

**现象 2：前后矛盾。**
你说"用中文回答"，它答应了。下一轮它突然用英文——因为"它答应过"这件事没被记录。

**现象 3：重复追问。**
你说了名字，它问了第二遍。因为在它眼里，你从来没说过。

**现象 4（最隐蔽）：成本反而变低，让你误以为优化成功。**
漏存 assistant 会减少 token，你会看到账单变小，以为是好事——**其实是功能坏了。**

> 这题的真正考点：**"省 token"和"功能正确"经常冲突，你必须先保证后者。**

## 第 3 题 · 雪球有多大

### 第 1 问：第 20 轮发多少

每轮新增 300 token（问+答），system 固定 50。

第 20 轮时，历史里已有 19 轮的对话：

```
300 × 19 + 300（本轮） + 50（system）
= 5700 + 300 + 50
= 6050 token
```

### 第 2 问：20 轮累计

每轮发送量：第 n 轮 = 50 + 300n

```
总和 = 20 × 50 + 300 × (1+2+...+20)
     = 1000 + 300 × 210
     = 1000 + 63000
     = 64000 token
```

折合：`64000 / 1,000,000 × 2 元 = 0.128 元`

> **看起来不多？** 那是因为只有 20 轮、单价低。**如果是 1000 个用户同时在聊，就是 128 元/天。** 再乘 30 天 = 3840 元/月。

### 第 3 问：加滑动窗口后

从第 11 轮起，每轮只发 10 轮历史（3000 token）+ system 50。

- 第 1~10 轮：同前，`10×50 + 300×55 = 500 + 16500 = 17000`
- 第 11~20 轮：每轮固定 `3000 + 300 + 50 = 3350`，共 10 轮 = `33500`

```
总计 = 17000 + 33500 = 50500 token
```

**省了**：`(64000 - 50500) / 64000 ≈ 21%`

> 省 21% 听起来不多，但**对话越长，省的越多**。如果聊 100 轮，滑动窗口能省 80% 以上。
> 更重要的是：**不加窗口，第 100 轮会直接超出上下文上限，程序报错。**

### 常见错误

- ❌ 忘记加 system
- ❌ 把"20 轮累计"算成 `20 × 第20轮的量`（错，那是平均数乘以轮数，不是真实累加）
- ✅ 高分答案会指出：**"省钱是次要的，防崩溃是主要的"**

## 第 4 题 · 写截断函数

### 参考答案

```python
def trim(messages, max_turns=10):
    """
    保留 system + 最近 max_turns 轮（1 轮 = 1 问 + 1 答）。
    不修改原列表。
    """
    if not messages:
        return []

    # 分离 system 和历史
    if messages[0]["role"] == "system":
        system = [messages[0]]
        history = messages[1:]
    else:
        system = []
        history = messages

    # 处理奇数条：如果最后一条是 user（还没回答），它单独算"半轮"
    # 这里选择保留它（因为它是用户刚问的，最重要），但把它从"配对"计算里拿出来
    tail_user = []
    if history and history[-1]["role"] == "user":
        tail_user = [history[-1]]
        history = history[:-1]

    # 现在 history 应该是一问一答成对的
    keep = history[-(max_turns * 2):] if max_turns > 0 else []

    return system + keep + tail_user
```

### 3 个测试用例

```python
# 用例 1：正常，10 轮，只留 2 轮
msgs = [{"role": "system", "content": "s"}]
for i in range(10):
    msgs.append({"role": "user", "content": f"q{i}"})
    msgs.append({"role": "assistant", "content": f"a{i}"})

out = trim(msgs, 2)
assert len(out) == 5                      # system + 2 轮
assert out[1]["content"] == "q8"           # 留下最近的
assert out[-1]["content"] == "a9"
assert len(msgs) == 21                     # 原列表未被修改 ✅

# 用例 2：奇数条（最后一条 user 没回答）
msgs2 = [
    {"role": "system", "content": "s"},
    {"role": "user", "content": "q0"},
    {"role": "assistant", "content": "a0"},
    {"role": "user", "content": "q1"},     # 还没回答
]
out2 = trim(msgs2, 1)
assert [m["content"] for m in out2] == ["s", "q1"] or len(out2) == 3
# 具体保留策略见下

# 用例 3：空列表
assert trim([], 5) == []
```

### 边界处理说明（这是本题真正考的地方）

| 边界 | 处理方式 | 理由 |
|---|---|---|
| 最后一条是 `user`（未回答） | **优先保留**，因为它是最新问题 | 砍掉它等于用户白问了 |
| 没有 `system` | 不要硬插一条空的 | 会让模型困惑 |
| `max_turns=0` | 只留 system + 当前问题 | 这是一种合法配置（"完全失忆模式"） |
| 原列表 | 用切片返回新列表 | 原地 `pop` 会让调用方拿到意外的数据 |

> **在真实项目里，这 4 个边界里至少 2 个会在上线第一周被用户撞到。**

## 第 5 题 · 流式的三个坑

### 问题 A：`NoneType`

**原因**：流式返回的每个 chunk 里，`delta.content` **可能是 `None`**。典型出现在：

- 第一个 chunk（只有 role，没有 content）
- 最后一个 chunk（只有 `finish_reason`，没有 content）

**修改**：

```python
delta = chunk.choices[0].delta.content or ""
```

### 问题 B：没有打字机效果

**原因**：三个可能

1. 网络太快、内容太短，看起来就是一次性出来（正常，用长回答测）
2. `print` 没有 `flush=True`，Python 缓冲住了
3. 你在 GUI 里用的是"先拼完整再显示"的逻辑

**修改**：`print(delta, end="", flush=True)`

### 问题 C：`resp.usage` 是 None

**原因**：流式模式下，**服务端默认不返回 usage**（因为它逐块发送，前面的块发出去时还不知道总数）。

**解法（三选一）**：

| 方法 | 做法 | 精度 |
|---|---|---|
| 估算 | `prompt_tokens ≈ 输入字数/2`，`completion_tokens ≈ 输出字数/2` | 差 10~20% |
| 用 `include_usage` 参数 | 部分接口支持在最后一个 chunk 返回 usage | 准 |
| 关闭流式单独查 | 再发一次非流式请求 | 准但要多花钱 |

```python
# 方案二示意（是否支持看你用的接口文档）
stream = client.chat.completions.create(
    ...,
    stream=True,
    stream_options={"include_usage": True},
)
for chunk in stream:
    if chunk.usage:            # 最后一个 chunk 才有
        print("用量：", chunk.usage)
```

### 修改后的完整代码

```python
stream = client.chat.completions.create(
    model="deepseek-chat",
    messages=messages,
    stream=True,
)

full = ""
for chunk in stream:
    if not chunk.choices:
        continue
    delta = chunk.choices[0].delta.content or ""
    if delta:
        print(delta, end="", flush=True)
        full += delta

print()   # 换行
messages.append({"role": "assistant", "content": full})
```

**注意最后一行**：流式模式下，你必须**自己拼出完整回答**，再存回 messages。**否则下一轮它就不知道自己说过什么了**——这是流式 + 记忆结合时最容易漏的一步。

### 常见错误

- ❌ 只处理 A，不处理 C。**C 不会报错，只会让你算不出成本**，更隐蔽。
- ✅ 高分答案会指出：**流式 + 记忆 = 必须手动拼接 full 再 append**。

## 第 6 题 · 该不该用流式

| # | 场景 | 用吗 | 理由 |
|---|---|---|---|
| 1 | 网页 AI 聊天 | ✅ **必须用** | 首字延迟决定体验。用户等 5 秒没反应会关页面 |
| 2 | 批量打标签脚本 | ❌ **不该用** | 没人看过程。流式反而增加网络分片开销，还拿不到 usage |
| 3 | 生成后存进 Word | ❌ **不该用** | 用户看不到过程，只关心最后成品。流式还会让"中断/重试"逻辑变复杂 |
| 4 | 实时语音助手 | ✅ **该用** | 边生成边转语音，延迟越低越自然。这正是语音助手的核心指标 |

### 判断口诀

> **"有没有人在实时看着" → 有就用，没有就不用。**

再补一条：**"需不需要精确统计成本"**。批量任务通常要算账，流式会让你算不准，这也是不用的理由。

## 第 7 题 · 找出"记忆的临界点"

### 参考做法

```python
messages = [{"role": "system", "content": "你是一个助手。"}]

def ask(q):
    messages.append({"role": "user", "content": q})
    resp = client.chat.completions.create(
        model="deepseek-chat", messages=messages, temperature=0
    )
    ans = resp.choices[0].message.content
    messages.append({"role": "assistant", "content": ans})
    return ans, resp.usage.total_tokens
```

测试流程：

```
ask("我的名字是李雷，请记住。")
ask("今天天气怎么样？")      # 无关问题 1
ask("讲个笑话")              # 无关问题 2
ask("1+1 等于几")            # 无关问题 3
ask("给我推荐一本书")         # 无关问题 4
ask("用一句话总结我们刚才聊了什么")  # 无关问题 5
ask("我叫什么名字？")         # 关键测试
```

### 参考观察

**不加截断时**：第 7 步仍能答对"李雷"。
原因：总共才 7 轮，远没到上下文上限（几万 token）。

**加上 `trim(messages, max_turns=2)` 后**：第 7 步**答不出来**。
因为它只保留了最近 2 轮（"总结我们聊了什么" + 回答 + "我叫什么"），**名字早被砍掉了**。

### 一句话总结（参考答案）

> **"记忆"和"上下文长度"成反比：留得越多，越不容易忘，但也越贵越慢；留得越少，越便宜越快，但也越健忘。**

### 这题真正想让你体会的

**"AI 失忆"往往不是模型的锅，是你截断策略的锅。**

真实产品里，解决"忘了名字"的正确做法不是"把窗口调大"，而是：

1. **把重要信息提取出来，放进 system**（比如"用户叫李雷"），这样它永远在，且只占几个 token
2. 或者做"用户画像"存储（这就是 M4 的 RAG 思路用在对话上）

> 这就是从"会用 API"到"会做产品"的那一步。
