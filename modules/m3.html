【这一讲要解决什么】

学完这一讲，你能：

  1. 解释"为什么关键词搜索不够用"，并说出它会失败的 3 种典型情况
  2. 用一句话解释 Embedding（向量） 是什么，不用任何数学
  3. 自己写代码：把句子变成向量 → 算相似度 → 排序 → 返回最像的
  4. 知道什么时候语义检索会输给关键词搜索（这点比会用更重要）

一、关键词搜索的三个死穴

你在文档里按 Ctrl+F 搜"退款"，这是关键词匹配：字面一样才算命中。

它会在三种情况下彻底失效：

情况例子结果
同义词你搜"退货"，文档里写的是"退还商品"搜不到
跨语言你搜"退款"，文档是英文 "refund policy"搜不到
表述不同你搜"东西坏了能换吗"，文档写"商品质量问题支持换货"搜不到

而人不是这么找东西的。你说"东西坏了能换吗"，你脑子里已经知道这和"质量问题换货"是一回事——你比的是"意思"，不是"字"。

语义检索要做的，就是让电脑也学会比"意思"。

二、Embedding：把一句话变成一个"坐标"

核心比喻：把每句话放到一张巨大的地图上

想象有一张地图：

  • 意思相近的句子，住得近
  • 意思无关的句子，住得远

"如何申请退款"和"钱怎么退回来"，这两句话在这张地图上是邻居。 "如何申请退款"和"今天天气不错"，一个在城东一个在城西。

Embedding（嵌入）就是"算出这句话在地图上的坐标"这件事。

只不过这张地图不是 2 维的，而是 几百到几千维的（常见 768、1024、1536、3072）。人脑想象不了 1536 维，但电脑算距离毫无压力。

一句话定义

Embedding = 把一段文字，转换成固定长度的一串数字。这串数字代表它的"意思坐标"。

为什么这招有效（不用公式的解释）

模型在训练时读过海量文本。它学到一件事："在相似的上下文里出现的词，意思应该相近"。

比如"退款"和"退货"经常出现在同一类句子里，"退款"和"天气"几乎不一起出现。训练的結果就是：前者坐标接近，后者坐标远离。

这个思想叫"分布式假设"：一个词的意思，由它周围常出现的词决定。 你不需要记这个名字，只需要记住"住得近 = 意思近"。

三、怎么算"近"：余弦相似度

直觉

两个向量之间可以算"夹角"：

  • 夹角小（方向一致）→ 相似度高，接近 1
  • 夹角90°（垂直）→ 无关，接近 0
  • 夹角大（方向相反）→ 负相关，接近 -1

余弦相似度就是这个夹角的余弦值，范围 -1 到 1。

为什么用"方向"而不是"距离"

因为长度不重要，方向才重要。

"退款"和"我要申请退款，因为商品有质量问题，希望尽快处理"——后者字数多、向量"长"，但它们说的是同一件事，方向一致。

用方向比，长短不影响；用直线距离比，长句子会被"冤枉"。

四、Embedding 从哪来：三个现实选择

⚠️ 一个你必须知道的事实

不是所有大模型厂商都提供 embedding 接口。

比如 DeepSeek 目前（以官网为准）主推对话模型，没有 embedding 接口。所以到 M3 你会发现：

"聊天"和"向量"往往是两个不同的服务，甚至两家不同的公司。

这不是坏事，这是真实工程的样子。你的架构要能容纳"多厂商"。

三条路

方案代表优点缺点适合
A. 国内 API智谱 embedding-3、阿里百炼 text-embedding-v*中文效果好、免部署、便宜要注册新账号、要联网推荐
B. 聚合平台硅基流动等，OpenAI 兼容一个 key 调多种模型多一层中间商备选
C. 本地模型sentence-transformers + bge-small-zh免费、离线、数据不外传要下载几百 MB，CPU 慢一点数据敏感时

对你的建议：先用 A（注册一个 embedding 服务），跑通全流程。等 M5 要反复做实验时，再考虑 C（省 API 调用费）。

五、向量库：为什么不直接存成一个 list

你可以把所有向量存进一个 Python 列表，查询时暴力算一遍。几十条数据完全够用。

但数据一多就崩：

数据量暴力算法（numpy）需要向量库吗
100 条毫秒级不需要
1 万条几十毫秒勉强
100 万条几秒~几十秒必须

向量库（Chroma、FAISS、Milvus、Qdrant…）帮你解决四件事：

能力说明
近似最近邻（ANN）不追求 100% 精确，用索引换速度，毫秒级返回
持久化存硬盘，重启不丢
元数据过滤"只在 2024 年的文档里搜"
增删改不用每次全量重算

你只需要会四个动作

⚠️ Chroma 默认会自己下一个 embedding 模型，这会让你以为"我在用 API 的向量"，其实是两套东西混在一起。一定要显式传入自己的向量，否则你会得到莫名其妙的排序。

这是新手在 Chroma 上最常踩的坑，没有之一。

六、五个决定效果的工程细节

这些细节，教程很少讲，但直接决定"你的搜索是不是好用"。

细节说明建议
① 归一化存之前把所有向量长度变成 1一定要做，省事又提速
② 批量一次传 32/64 条，不要一条一条调快 10 倍，还可能更便宜
③ 相似度阈值低于某个分数就认为"没有相关内容"关键！否则永远返回 top-1，哪怕完全不相关
④ top-k 的选择k 太小漏，k 太大吵3~5 起步，M5 再调
⑤ 文本要"干净"去掉页眉页脚、乱码、重复空行脏数据会污染向量

关于 ③ 阈值（最重要）

没有阈值的搜索，是"必须给你一个答案"的搜索。

用户问"怎么给猫剪指甲"，你的知识库全是退款政策。没有阈值 → 它会把最像的那条退款政策硬塞给你。用户看到的就是"这 AI 在胡说"。

"敢说不知道"，是检索系统成熟的标志。 这句话在 M4/M5 会反复出现。

七、语义检索的三个死穴（你必须知道）

语义检索不是万能药。它在下面这些场景会输给关键词搜索：

场景为什么例子
精确标识符向量不理解"字符级"的精确匹配搜订单号 A20240315001，语义检索可能返回一堆别的订单
否定与数量"不含糖"和"含糖"在向量空间非常接近搜"不含防腐剂的食品"可能返回"含防腐剂"
罕见专有名词训练时没见过，向量不准搜内部项目代号"凤凰计划"

所以工业界的正确答案是：混合检索

关键词（BM25）+ 语义（向量），两路都跑，再合并排序。这叫 Hybrid Search，是 M5 的核心内容。

记住这个判断：用户搜的是"概念"→ 用向量；用户搜的是"编号/代码/精确词"→ 用关键词；不知道 → 两个都用。

【常见误解】

误解 1："Embedding 是加密/压缩。" 不是。它是语义映射，不可逆（你没法从向量还原原文），也不保证保真（相似的意思可能被映射得不够近）。

误解 2："维度越高越好。" 不一定。高维更细，但更慢更贵，而且在数据量小时反而容易"过拟合噪声"。中小规模用 512~1024 维足够。

误解 3："相似度高就一定相关。" 不一定。向量只捕捉"语义相近"，不捕捉"是否回答了问题"。问"退款流程"，可能召回"退款政策说明"——很像，但不是你要的。这就是 M5 要上"重排（rerank）"的原因。

误解 4："用了向量库就不用管数据质量了。" 完全相反。垃圾进，垃圾出，而且向量库会让垃圾看起来"很有道理"（因为它总能返回 top-3）。

💻 第 3 题（代码）· 实现最小语义搜索

写一个脚本，完成：

  1. 准备 6 条文本（你自己编，比如 6 条商品描述）
  2. 调用 embedding 接口，一次性批量拿到 6 个向量
  3. 保存到 vectors.json（格式：[{"text": "...", "vec": [...]}, ...]）
  4. 输入一个查询，算出它和 6 条的相似度，按分数从高到低打印前 3 条
  5. 加一个阈值：低于 0.5 的不要

要求：不要用第三方向量库，用 numpy 手写。这一步必须自己写一遍，否则你不会真正理解向量库在干什么。

🔧 第 4 题（排错）· 三个"看起来能跑但结果不对"

问题 A：你用 Chroma 存了文档，但没有传 embeddings 参数，直接 col.add(documents=[...])。查询时传的是你自己算的向量。结果排序完全乱套。

问题 B：你换了 embedding 模型（从 1024 维换到 1536 维），但旧的 vectors.json 没删。程序报错。

问题 C：你存向量时没做归一化，有两个文本，一个是短句、一个是长段落，讲的是同一件事，但短句的相似度分数总是偏低。

任务：逐个说明原因和修法。特别注意 A，这是 Chroma 上最常见、也最难发现的坑。

第 1 题 · 三种死穴

第 1 问：分别属于哪种

#类型说明
1表述不同（近义但字面不同）"请假怎么请" vs "休假申请流程"，没有共同的关键词
2跨语言中文库、英文查询，字面零重叠
3同义词 / 口语 vs 书面语"加班" vs "延时工作"，"补贴" vs "补偿"

严格说，1 和 3 都属于"词汇不匹配（vocabulary mismatch）"。分三类是为了让你记住触发条件是"字面不同"。

第 2 问：语义检索为什么能搜到

因为 embedding 是在大量真实语料上学的，它见过：

  • "请假"和"休假"经常出现在同一类句子里
  • "refund"和"退款"在中英对照语料里是邻居
  • "加班补贴"和"延时工作补偿"是同一个概念的不同说法

所以它们的坐标很近，即使一个字都不重合。

关键认知：语义检索不看你用了什么词，只看你的意思落在哪。

第 3 问：一个语义检索也会失败的制度类查询

参考答案：

搜"年假有多少天"。

失败原因：制度里可能有一张表格（"工龄 1-3 年：5 天；3-10 年：10 天"），表格在向量化时会被压成一段文字，"你的工龄"这个条件被丢了。向量只捕捉了"年假、天数"的语义，无法做"按我的工龄查表"这种条件计算。

其他好答案：

  • "报销标准是每小时多少钱"——需要数值精确匹配，向量不擅长
  • "第 3.2 条说的是什么"——需要精确定位条款编号，关键词更准

这题想让你明白：语义检索解决"表述不同"，不解决"计算"和"精确定位"。 后者要靠结构化查询或工具调用（M6）。

第 2 题 · 手算余弦相似度

第 1 问：三个值

公式：cos = (A·B) / (|A| × |B|)

① A=[1,0]，B=[1,1]

② A=[1,0]，B=[-1,0]

③ A=[1,2]，B=[2,4]

第 2 问：为什么 ③ 是 1

因为 [2,4] = 2 × [1,2]，两个向量方向完全相同，只是长度差 2 倍。

而余弦只看夹角，不看长度。

结论：余弦相似度衡量的是"方向是否一致"，不是"距离有多近"。

这也解释了为什么短句和长段落说同一件事时，余弦相似度依然很高——这正是我们想要的行为。

第 3 问：归一化后还能用点积吗

能。而且必须用。

推导（一行）：

所以工程上标准做法是：

  1. 入库前把每条向量归一化
  2. 查询时把查询向量也归一化
  3. 直接用点积（矩阵乘法）批量算，一次算 100 万条也只要毫秒级

这就是"为什么所有向量库都默认归一化"的原因：不只是数值稳定，更是为了能用矩阵乘法提速。

常见错误

  • ❌ ② 算成 0。方向相反是 -1，不是 0；垂直才是 0。
  • ❌ ③ 看到长度不同就以为相似度低。这是最典型的直觉错误。

常见错误

  • ❌ 用 for 循环一个个算余弦，再 sorted。能跑，但慢 100 倍，而且没机会体会矩阵乘法的好处。
  • ❌ 存的时候归一化，查的时候忘了。分数还是对的（因为除法抵消），但你会困惑"为什么点积能当余弦用"。
  • ✅ 高分答案会把"查询文本"和"库文本"用同一个模型编码。用了两个不同模型，分数完全无意义——这是比什么都重要的铁律。

第 4 题 · 三个"看起来能跑但结果不对"

问题 A：Chroma 没传 embeddings

原因：Chroma 在 add() 时如果不给 embeddings，会自动用它的默认 embedding 函数（通常是一个内置的 ONNX 小模型，会静默下载）。

于是：库里存的是默认模型的向量，查询时你传的是你自己模型的向量。

两套坐标系统，混在一起比距离。 结果就是随机排序，而且不报错。

修法：

如何验证你在踩这个坑：

维度对不上（比如你的是 1024，出来是 384）→ 中招了。

问题 B：换模型后旧向量没删

原因：不同模型的向量空间互不兼容。1024 维和 1536 维连矩阵乘法都做不了，直接报维度错。

即使维度碰巧相同（比如两个模型都是 1024 维），空间也不同，分数毫无意义。

修法：

  1. 删除旧库/旧 json
  2. 全量重算
  3. 在库里记录模型名和维度（比如 collection 名字带上 _bge_1024），避免以后混用

这是工程上的重要习惯：向量数据必须和"生成它的模型"绑定。 换模型 = 全量重建，没有捷径。

问题 C：没归一化导致短句分数偏低

原因：这题是个"陷阱题"——如果用的是余弦相似度，归一化与否结果相同（除法会抵消）。

真正会导致"短句分数偏低"的原因通常是：

  1. 你用的是点积或欧氏距离，而不是余弦
  2. 长段落里混进了大量无关内容，把语义"稀释"了（这是真的，不是归一化的问题）

修法：

  • 统一用余弦（或先归一化再用点积）
  • 对长文本做切分（chunk），别把一整段塞成一个向量 —— 这正是 M4 要讲的
  • 给标题/关键句更高权重（M5 的混合检索）

这题的设计意图：让你学会区分"归一化问题"和"长文本稀释问题"。 它们的症状像，病因完全不同。

常见错误

  • ❌ 认为 A 会报错。它不报错，这才是最坑的。
  • ✅ 高分答案会提出"给 collection 名字加模型标识"这种工程习惯。

"能一字不差打出来的" → 关键词；"只能描述出意思的" → 语义。

你会看到一条典型曲线：阈值低 → 误召回多；阈值高 → 漏召回多。中间有个"甜点"。

1. 项目要做什么

一句话

给你自己的 20~50 条笔记/收藏/商品描述，做一个按意思搜索的小工具：输入"怎么把钱要回来"，它能找到"退款流程说明"。

验收标准

  • 有 ≥20 条自己的真实文本
  • 一次命令能建好索引，存成文件，重启不丢
  • 查询返回 top-3 + 分数
  • 有阈值：问库里没有的东西，会说"没找到"
  • 能一键切换 top-k 和阈值（不改代码）
  • 有一个网页界面（Streamlit）
  • 有一张自己填的"5 个查询"评测表

明确不做

  • ❌ 不做文档解析（PDF/Word）—— 那是 P5
  • ❌ 不做生成回答，只做检索 —— 这是关键区别
  • ❌ 不做重排、混合检索 —— 那是 M5

这一版只做"找"，不做"答"。 先把"找得准"这件事做扎实，M4 才有意义。

3. 项目文件结构

为什么 embed.py 要单独一个文件

因为"换 embedding 模型"是必然会发生的（换厂商、升级模型、换成本地）。把它关在一个文件里，将来只改一处。

接口越窄，越好维护。 这是软件工程最朴素也最有用的一条。

三个必须看懂的连线

  1. 建索引和查询必须用同一个模型（图里我特意标了"同一模型！"）。混用 = 分数无意义。
  2. 归一化在两边都要做，这样才能用矩阵乘法。
  3. 阈值判断在排序之后，判断的是"最高分"，不是"每条都判断"。
