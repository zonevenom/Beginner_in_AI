【这一讲要解决什么】

学完这一讲，你能：

  1. 判断你的应用该"部署到哪"（三种方案，各有适用场景）
  2. 正确管理密钥（这一条做错，后果最严重）
  3. 用 FastAPI 把功能包成一个接口，知道什么时候需要它
  4. 加限流，防止被别人刷爆你的账户
  5. 把三个项目包装成一份能投的作品集

一、先搞清楚"上线"有三个层次

层次长什么样谁能用技术难度
L1 本地脚本streamlit run app.py只有你⭐
L2 内网/临时链接局域网 IP / 临时隧道你和同事⭐⭐
L3 公网服务https://xxx.com任何人⭐⭐⭐

大多数人卡在 L1 到 L2 之间，不是因为技术难，是因为"没做过，不知道从哪下手"。

这一讲就是把这条路走通。

二、三种部署方案，怎么选

方案 A：Streamlit Community Cloud（最快，免费）

项说明
怎么做代码推到 GitHub → 在 share.streamlit.io 点几下 → 拿到链接
成本免费
限制需要 GitHub；国内访问速度一般；资源小（内存 1G 左右）
适合你的 P3/P5/P6/P7

这是你该先走的路。 从"没部署过"到"有链接"，最快 20 分钟。

方案 B：Hugging Face Spaces（免费，AI 圈常用）

项说明
怎么做建 Space → 选 Streamlit/Gradio → 上传文件
成本免费（CPU 基础版）
限制需要 HF 账号；国内访问需要条件
适合想让海外同行/招聘方看到

方案 C：国内云服务器（要花钱，但最"真"）

项说明
怎么做买一台轻量应用服务器（2 核 2G 起）→ 装 Python → 跑服务 → 配域名
成本新用户首年通常有优惠，之后每月几十元
限制要会一点 Linux；要备案（用域名的话）
适合想写"独立部署"进简历；或要给国内用户稳定访问

🛑 买服务器之前先问我。 我会告诉你买什么配置、有没有必要买、怎么避免"买了一台不会用"。

方案 D：内网穿透（临时演示用）

一行命令把本地端口暴露成公网地址（如 cloudflared tunnel、ngrok）。

优点：立刻能用，零配置。 缺点：电脑一关就断，且地址每次变。

只适合"临时发给朋友看 5 分钟"，不适合写进简历。

选择建议

三、密钥管理：这一节做错，会真出事

三种错误做法（每一种都有人踩）

❌ 做法后果
把 key 写进代码推到 GitHub 后，几分钟内被爬虫扫走，当天账单爆掉
把 .env 一起提交同上。.gitignore 忘了写 .env，等于没写
把 key 写在 Streamlit 界面的输入框里用户能看到、能复制、能拿去用你的钱

✅ 正确做法

本地开发：.env + .gitignore

Streamlit Cloud：用 st.secrets

云服务器：系统环境变量，或 systemd 的 EnvironmentFile

一条铁律

密钥只存在于"运行环境"，不存在于"代码仓库"。

检查方法（在项目目录执行）：

有输出 = 你已经泄露了，立刻去平台吊销那个 key 重新生成。

四、什么时候需要 FastAPI（而不是 Streamlit）

Streamlit 有个硬限制：它是给人点的，不是给程序调的。

场景用 Streamlit用 FastAPI
你自己/同事在网页上问问题✅也可以
别的程序要调用你的能力❌✅
要做成微信机器人/小程序后端❌✅
要返回 JSON 给前端❌✅

最小 FastAPI（20 行）

跑起来：uvicorn main:app --reload，然后访问 http://127.0.0.1:8000/docs——FastAPI 自动给你一个能点的接口文档页面。

这个 /docs 页面是 FastAPI 最香的地方：你不用写前端，就能测接口。

什么时候不需要 FastAPI

你现在不需要。 三个人用的小工具，Streamlit 足够。

加 FastAPI 的唯一理由是："有别的程序要调我"。没有这个需求，加了只是多一层。

面试时被问"为什么用 Streamlit 不用 FastAPI"，答"因为我的用户是人不是程序，Streamlit 让我 2 小时做出界面"——这是加分回答。

五、上线后必须做的四件事

① 限流（防刷）

你的 key 挂在公网，就有人能刷。哪怕是免费的额度，也会被刷光。

更简单的做法：每次请求之间 time.sleep(1)，或在界面上禁用按钮直到返回。

② 输入长度限制

为什么：一次 10 万字的问题，可能直接烧掉你几块钱。

③ 日志

没有日志，出问题你只能靠猜。

④ 错误兜底

用户不需要看堆栈，你需要看日志。 两者分开。

六、作品集：三个项目怎么包装

你手里有什么

项目技术点可量化成果
P5 RAG v1解析/切分/检索/生成/引用10 题评测
P6 RAG v2混合检索/父块/评测体系命中率 62%→81%
P7 AgentFunction Calling/工具设计/刹车6 任务 + 3 破坏测试

这三个是递进的：从"能用"到"好用"到"会决策"。这个递进关系本身就是故事。

README 的标准结构（每个项目都要有）

"我踩过的坑"这一节，是最值钱的一节

因为它证明你真的做过。招聘方看 10 份 README，9 份都在吹功能，只有 1 份在讲踩坑——那份会被记住。

例子：

坑：Chroma 默认会用自己的 embedding 模型 我传了自定义向量但没传 embeddings 参数，导致库里存的是另一套坐标系的向量。查询不报错，但排序完全随机。排查了两小时才发现要用 col.get(include=["embeddings"]) 看实际维度。

简历三句话（照这个模板写）

① 做了什么：独立实现文档问答系统，支持 PDF 解析、语义检索与答案溯源。 ② 怎么做的：自建 20 题评测集，量化 Recall/Precision；通过父块扩展与 BM25 混合检索优化检索层。 ③ 结果如何：整体答对率从 60% 提升至 80%，精确信息类问题从 33% 提升至 100%。

注意每一句都有"动词 + 方法 + 数字"。 没有数字的简历句，等于没写。

面试会被问什么（提前准备）

问题你要能答出
"你的 RAG 怎么评估的？"20 题、四指标、怎么标 gold
"为什么用混合检索？"向量擅长语义、BM25 擅长精确词，RRF 融合因为量纲不同
"Agent 怎么防死循环？"步数上限、重复签名检测、错误回传
"密钥怎么管的？".env + .gitignore + 平台 secrets，从不在代码里
"如果用户量涨 100 倍怎么办？"缓存、限流、向量库换 Milvus、异步、成本监控

最后那个问题没有标准答案，它考的是你有没有想过。

【常见误解】

误解 1："部署就是把代码传上去。" 不。部署要处理：依赖版本、密钥、端口、日志、限流、错误兜底。传代码只占 20%。

误解 2："Streamlit 做的不是真产品。" 对，它不是。但它能让你在 2 小时内验证想法。产品化是后面的事，别在验证阶段就追求产品级。

误解 3："免费额度够用，不用管限流。" 错。公网链接一旦被转发到群里，十分钟就能刷光。限流不是"以防万一"，是"必然需要"。

误解 4："作品集要有 5 个项目才够。" 错。3 个做深 > 10 个做浅。 面试官会挑一个往死里问，你答不出细节就完了。

🧠 第 4 题（概念）· 密钥的四种写法

判断下面 4 种做法是否可以接受，说明理由：

  1. api_key = "sk-abc123..." 直接写在 app.py 里，但没有推到 GitHub
  2. api_key = os.getenv("DEEPSEEK_API_KEY")，.env 写在 .gitignore 里
  3. 在 Streamlit 界面做一个输入框，让用户填自己的 key
  4. 用 st.secrets["DEEPSEEK_API_KEY"]，secrets.toml 不提交

第 1 题 · 该部署到哪

#选择理由
1内网穿透今晚就要，零配置。缺点（地址会变、电脑要开着）在这个场景不重要
2Streamlit Cloud（或国内云）要"长期活着 + 点开就能用"。Cloud 免费且稳定；如果面向国内用户、要更稳，选国内云
3HF Spaces海外访问快，AI 社区习惯在这看 demo
4内网服务器不能上公网 → 只能在公司内网跑，或用 Docker 部署到内网机器

判断口诀

"给谁看、看多久、在哪看" —— 三个问题定方案。

  • 给谁：自己/朋友 → 临时；招聘方 → 稳定；海外 → HF
  • 看多久：5 分钟 → 穿透；3 个月 → Cloud；长期 → 云服务器
  • 在哪：公网 / 内网 / 海外

常见错误

  • ❌ 第 1 题选 Cloud。部署 Cloud 要推 GitHub、等构建，20 分钟起步，而穿透 1 分钟。场景决定方案，不是"越正式越好"。

第 2 题 · 补全接口

第 1 问：补全

第 2 问：/health 的作用

三个用途：

用途说明
存活探测云平台/负载均衡定期访问它，返回 200 就认为服务活着
部署验证部署完先访问 /health，能通说明"服务和路由都对"，再去测业务接口
快速定位业务接口 500 时，先访问 /health：通了 → 业务逻辑问题；不通 → 服务本身没起来

这是"排查分层"的思路：先确认"活着"，再确认"能干活"。

第 3 问：防护

防护做法
限流每个 IP 每分钟最多 N 次（slowapi 库，或自己用字典记时间戳）
鉴权加一个 X-API-Key 头，只有知道 key 的人能调
输入上限问题长度、top_k 上限（你已经做了）
预算熔断当天累计 token 超过阈值就返回 503
CORS 白名单只允许你的前端域名调用

最低配也要做"限流 + 长度限制"。 这两个加起来能挡住 90% 的"无意刷爆"。

第 3 题 · 上线后的四个"灵异事件"

A：ModuleNotFoundError: No module named 'pypdf'

原因：requirements.txt 里没有 pypdf（或拼错了）。

排查：

  1. 看部署平台的构建日志，找 pip install 那一段
  2. 本地 pip freeze | findstr pypdf 确认版本
  3. 补进 requirements.txt，重新部署

根因：本地能跑是因为你装过，云端是全新环境。 这是"本地 vs 云端"第一课。

预防：养成习惯——只在 requirements.txt 里列依赖，不在本地全局环境里随意 pip install。

B：页面能开，点发送就白屏

原因（按概率）：

  1. 异常没被捕获，Streamlit 把整个脚本崩了 → 页面空白
  2. 前端 JS 报错（少见）
  3. 无限循环导致超时

排查：

  1. 看平台日志（Streamlit Cloud 有 "Manage app" → 日志）
  2. 本地复现：streamlit run app.py，看终端有没有红色堆栈
  3. 在白屏前的位置加 st.write("到了这里 1") 打点

修法：所有外部调用（API、文件、模型）都包 try/except，出错时 st.error("...")。

C：用了三天突然 401

原因：key 失效了。三种可能：

可能怎么确认
余额耗尽登录平台看账单
key 被平台自动吊销（检测到泄露）平台有安全通知
你换了 key 但没更新 secrets对比代码和平台配置

排查：先在本地用同一个 key 跑一次。本地也 401 → key 的问题；本地正常 → 部署环境的配置问题（比如 secrets 名字拼错）。

D：部署后 30 秒，本地 3 秒

原因：

原因说明
冷启动免费平台会休眠，第一个请求要唤醒容器（10~30 秒），这是最常见原因
网络云端调 API 的链路更长
资源小免费版 CPU 只有 0.1~1 核
每次重建索引如果你的代码在启动时重算 embedding，那每次冷启动都要重跑

排查：连续请求 3 次，看是不是只有第 1 次慢。只有第 1 次慢 = 冷启动，这是正常现象，不是你代码的问题。

优化：

  • 把"建索引"改成离线做好、直接加载文件（P5 的 store.load() 就是这个思路）
  • 用 @st.cache_resource 缓存模型/索引

@st.cache_resource 是 Streamlit 最重要的装饰器：它让"加载索引"只做一次，而不是每次交互都做。

关于"裸环境验证"

这是本项目最重要的一步，也是最容易被跳过的一步。

为什么必须做：你在自己的环境里"能跑"，是因为你半年里陆续装了几十个包。别人拿到你的代码，只有 requirements.txt。

90% 的"部署失败"在这一步就能提前发现。在本地花 10 分钟，胜过在云端瞎猜 1 小时。

为什么"密钥扫描"要放在推 GitHub 之后、部署之前

因为推上去的那一刻就已经泄露了。扫描是为了立刻发现并止损，不是为了"预防"。

真正的预防是在 .gitignore 里写 .env——但那只能防"以后"，防不了"你已经在本地 commit 过"。
