【这一讲要解决什么】

学完这一讲，你能：

  1. 用四个指标说清你的 RAG 到底多好（而不是"感觉还行"）
  2. 诊断检索失败的四种病，对症下药
  3. 实现混合检索（关键词 + 向量）和重排（rerank）
  4. 建一套 20 题的评测集，做出"优化前 62% → 优化后 81%"这种结论

一、先承认一件事：你的 v1 一定不够好

P5 做完，你大概会遇到这些情况：

  • 明明文档里有，它就是找不到
  • 找到了，但答得不对
  • 答对了，但引用了三页不相关的内容
  • 问了个稍微绕一点的说法，直接崩

这不是你的错，是 RAG 的正常状态。 论文里叫它 "naive RAG"——朴素 RAG。

工业界的 RAG，普遍要在这个基础上做 3~4 轮优化。 这一讲就是那 3~4 轮。

二、先把"好"定义出来：四个指标

没有指标，你所有的优化都是玄学。RAG 至少要看四个数：

指标 1：Recall@k（召回率）—— 最核心

在召回的 k 条里，有没有"包含答案的那一条"？

  • 你建了 20 道题，每道题你都知道"答案在第几块"（这叫 gold chunk）
  • 检索 top-5，看这 5 条里有没有 gold chunk
  • 有 → 这题算命中

这是 RAG 的"生死线"：如果 gold chunk 不在召回结果里，后面的模型再强也没用——它根本没看到答案。

指标 2：Precision@k（精确率）

召回的 k 条里，有几条是相关的？

Precision 低说明"噪声多"，会让模型分心。

指标 3：答对率（Answer Accuracy）

人工判断：最终回答对不对（含"该拒答时拒答了"）。

这个最贴近用户感受，但要人工标注，成本高。

指标 4：引用正确率

回答里引用的页码，是不是真的支持那个结论。

这个指标最能体现"产品成熟度"，但大多数教程都不提。

四个指标一起看

场景Recall@5Precision@3答对率说明
A0.90.30.5检索到了但噪声大 → 加阈值/重排
B0.40.90.35找得准但找不全 → 加大 k/混合检索
C0.90.90.4检索完美但答不对 → 改提示词/换模型
D0.40.30.2全部要改，先改切分

这张表就是你的"体检报告"。 先看哪个低，再决定改哪里——不要瞎改。

三、检索失败的四种病

病 1：根本没召回（Recall 低）

症状：问"退款多久到账"，检索结果里全是"退款政策总则"这种大而空的块。

病因与药：

病因药
切分太碎，答案被切成两半加大 chunk_size / 加 overlap / 父子块
用户说法和文档说法差异大查询改写（下面讲）
只有向量检索，遇到精确词就废混合检索（下面讲）
文档本身没写（真没有）补文档，别硬调

病 2：召回了但排太后（Recall@5 低，Recall@50 高）

症状：top-3 里没有，但 top-10 里有。

病因：向量相似度排序不准。

药：重排（Rerank）——先粗召 30 条，再用更贵的模型精排出 top-3。

病 3：召回了但噪声多（Precision 低）

症状：top-5 里有 4 条不相关，模型被带偏，答得又长又乱。

药：加阈值、减小 k、加重排。

病 4：检索对了但答错（答对率低，Recall 高）

症状：gold chunk 在 context 里，但它还是答错。

药：这是生成层的问题：

  • 提示词没写"只用资料"
  • temperature 太高
  • context 太长，关键信息被"埋"在中间（lost in the middle）
  • 模型能力不足（最后才考虑换模型）

排查顺序永远是：先看检索，再看生成。 90% 的人一上来就换模型，白花钱。

四、四把武器

武器 1：查询改写（Query Rewriting）

用户的问法，往往和文档的写法差很远。

做法 A：多查询（Multi-Query）

让模型把一个问题改写成 3 个不同说法，分别检索，结果合并去重。

为什么有效：一句话可能"碰巧"命中，三个说法命中概率高得多。

代价：3 倍检索调用（但检索很便宜，主要是 embedding 调用）。

做法 B：HyDE（假设文档嵌入）

让模型先编一个假答案，然后拿这个假答案去检索。

为什么有效：假答案的"用词风格"更接近真实文档（都是陈述句、都用"工作日""原路退回"），而用户的提问风格（疑问句、口语）离文档远。

这招很反直觉，但效果实在。注意：编出来的内容只用来检索，绝对不能当答案。

做法 C：指代消解（多轮对话时）

先把"那如果是质量问题呢"改写成"质量问题导致的退款多久到账"，再检索。不消解，第二句必崩。

武器 2：混合检索（Hybrid Search）

向量检索擅长"意思"，关键词检索（BM25）擅长"精确词"。两个都要。

怎么融合？最常用的是 RRF（Reciprocal Rank Fusion，倒数排名融合）

不要被名字吓到，公式就一行：

人话：每个检索器给文档排个名，排名越靠前得分越高，然后把两个得分加起来。

  • k 通常取 60（经验值，防止分母为 0，也压平差距）
  • 一个文档在向量里排第 1、在 BM25 里排第 5，得分 = 1/61 + 1/65

为什么用"排名"而不是"分数"：因为向量相似度（0~1）和 BM25 分数（0~几十）量纲完全不同，不能直接相加。转成排名就统一了。

这个洞察是 RRF 的全部精髓：不同尺度的分数不能加，但排名可以。

武器 3：重排（Rerank）

思路：粗排用便宜的（向量，毫秒级，召 30 条），精排用贵的（Cross-encoder，几百毫秒，排 3 条）。

Cross-encoder 和向量检索的区别：

向量检索（Bi-encoder）Cross-encoder
怎么算问题和文档分别编码，算距离问题和文档拼在一起送进模型
速度快（可预计算）慢（每对都要跑一次）
精度中高（能看到两者的交互）

所以你不可能用它检索全库（10 万条要跑 10 万次），只能用来"精排少量候选"。

实现方式：

  • 商用 API：Cohere Rerank、Jina Reranker、国内几家厂商也有
  • 本地：sentence-transformers 的 BAAI/bge-reranker-*（CPU 也能跑，几百 MB）

🛑 装 rerank 模型前先问我。它要下载几百 MB，且需要确认你的 CPU 跑得动。

武器 4：上下文扩展（父子块 / 句子窗口）

思路：用小块检索（准），命中后把它周围的大段一起给模型（全）。

为什么有效：解决"切断了语义"的问题，且不增加索引复杂度（只是检索后多取几条）。

代价：context 变长，token 成本上升。扩展 1 块通常就够，别扩太多。

五、优化顺序（这比技术本身重要）

很多人一上来就上 rerank、换模型，结果白花钱。正确的顺序是：

flowchart TD A[① 先修数据] --> B[② 再修切分] B --> C[③ 加混合检索] C --> D[④ 加查询改写] D --> E[⑤ 加重排] E --> F[⑥ 最后才考虑换模型]
顺序做什么典型收益成本
①清洗脏数据、去掉页眉页脚、修表格10~20%极低
②调 chunk_size / overlap / 父子块5~15%极低
③混合检索（BM25 + 向量）5~10%低
④查询改写3~8%低（多几次调用）
⑤重排5~10%中（要模型/API）
⑥换更强的生成模型0~5%高

注意最后一行：换模型往往是收益最小、成本最高的一步。 这就是为什么"先修检索"是铁的纪律。

【常见误解】

误解 1："Recall 高就说明 RAG 好。" 不。Recall 高只说明"找得到"，答得对不对是另一回事（看第三节病 4）。

误解 2："重排能救一切。" 不能。如果 gold chunk 压根没进候选集（召回阶段就丢了），重排排不出来。重排只能优化"候选集里已有"的东西。

误解 3："top-k 越大越好。" 越大召回越高，但噪声也越多，且成本线性上升。正确做法：粗召大（30）、精排小（3）。

误解 4："评测是最后做的。" 错。评测要在优化之前就做。没有基线，你无法证明"优化有效"，只能说"感觉好了"。

第 1 题 · 看体检表开药方

参考答案

组诊断先改什么
ARecall 高、Precision 极低 → 噪声病加阈值、减小 k、加重排。别动切分
BRecall 低、Precision 高 → 漏召回病加大 k、混合检索（精确词问题）、父子块
C检索完美、答对率低 → 生成层病改提示词（"只用资料"）、降到 temperature=0.1、缩短 context
D全面崩、拒答 0 → 地基烂先修数据和切分，其他都别动

第 D 组的深意

"拒答正确率 0.00"意味着：该拒答的题，它一次都没拒。

这说明你的阈值形同虚设，或者提示词里根本没有"允许说不知道"这条规则。

一条 RAG 从不说"不知道"，是最危险的状态——因为它对任何问题都会给一个看似合理的答案。

排查顺序：先看阈值是不是设成了 0，再看提示词有没有拒答模板，最后才怀疑检索。

常见错误

  • ❌ A 组去调 chunk_size。Recall 已经 0.9 了，说明找得到，问题在"给太多"。
  • ✅ 高分答案会指出：A 组先加重排而不是先减 k，因为减 k 会掉 Recall。

第 5 问：重复块

怎么产生的：

  1. overlap 太大（500/400），相邻块内容高度重叠
  2. 同一段文字在 PDF 里出现两次（如摘要 + 正文重复）
  3. 父子块方案里，父块和子块被同时召回

影响：

方面影响
Precision被拉低（重复的不算新信息，但占名额）
Recall不变（该在的还在）
模型有害：同一个信息出现三遍，模型可能误以为"这很重要"，或直接抄三遍
成本浪费 token

修法：召回后按 page + 文本前缀 做去重；控制 overlap ≤ chunk_size 的 30%。

这题的设计意图：让你意识到"Precision 低"不一定是"检索不准"，也可能只是"重复太多"。

第 3 问：分数直接相加会怎样

假设：

  • 向量分：a=0.82，c=0.79
  • BM25 分：c=18.5，a=3.2

直接相加：

RRF：

问题在哪：BM25 的量纲是 0~几十，向量是 0~1。直接相加等于"BM25 说了算"，向量检索形同虚设。

有人会说"那我归一化再相加"。但归一化需要知道分布，而且不同查询的分布还不一样，很难做对。

RRF 用排名绕过了这个问题：不管你的分数是 0.8 还是 18.5，我只关心你排第几。 这就是"排名比分数更稳"的工程智慧。

常见错误

  • ❌ k 取 0 或 1。会导致除零或排名差距过大，第一名 1.0，第二名 0.5，太陡。
  • ❌ 忘记 start=1，用 0 开始。

第 2 问：search_multi

第 3 问：同一 chunk 被多次命中，分数怎么算

方案 A：RRF 累加（推荐）

同一块被 3 个查询命中，得 3 份分。"被越多查询命中"= 越可能是真的好。

方案 B：取最高相似度

什么时候用 B：当你发现"累加"会让一些"用词模糊但广泛相关"的块排到前面时。

我的建议：主排序用 RRF 累加，平局时用 best_score 决。 两个都留着，方便调试。

第 4 问：成本

项基线多查询
改写调用01 次（贵，是聊天模型）
embedding 调用1 次4 次（便宜）
检索计算1 次4 次（几乎免费）

总成本约 2~2.5 倍（改写那一次相对贵）。

值不值？ 取决于场景：

  • 用户问题说法多样、文档用词固定（如法律、医疗）→ 很值
  • 用户问题和文档用词本来就一致 → 不值
  • 有延迟要求（<1 秒）→ 不值（改写要多几百毫秒）

这就是"工程判断"：同一个技术，在不同场景下价值不同。 面试时能说出这句话，比会写代码更值钱。

第 5 题 · 加了重排反而变差

至少 3 个原因 + 验证方法

#原因怎么验证
1候选集太小（top-30 里压根没有 gold）算 Recall@30。如果只有 0.6，那重排再准也没用——先扩候选
2分数方向反了（把最低分当最高分）打印前 5 条的 rerank 分数，看是否和"人工判断的相关性"同向
3rerank 模型不适合中文/领域换一个中文模型对比；或人工看"它把 gold 排第几"
4重排后取 top-3 太激进试 top-5；对比答对率
5重排把"长块"惩罚了看被降权的块是否长度异常（有的模型偏爱短文本）
6模型被"看起来相关但没答案"的块骗了这是 rerank 的本质局限：它判断"相关性"，不判断"是否包含答案"

第 6 条最值得展开

Rerank 模型的训练目标是"相关性"，不是"可回答性"。

一个块可能大谈"退款政策的重要性"（高度相关），但不含"几天到账"这个具体答案。 一个块可能是"退款 3-5 个工作日到账"（直接答案），但语义上和问题只是"中等相关"。

于是 rerank 把前者排到前面，答对率反而下降。

这是 RAG 里一个很深的坑："相关"≠"有用"。 解法：用带答案标注的数据微调 rerank 模型（超出你的范围），或者同时保留向量排序和 rerank 排序，做加权融合。

常见错误

  • ❌ 只说"重排模型不好"。先排除候选集太小这个最常见的低级原因。

  2. 有归因（"因为短块更聚焦"）

2. 工具与开发环境

🛑 本项目的核心优化（父块 + 混合检索）零新增依赖。 rerank 是可选项，要装模型/开 API，动手前先问我。

项状态说明
Python + numpy + streamlit已有沿用 P5
jieba可选中文分词。先别装，本项目用"字符 bigram"替代
sentence-transformers可选本地 rerank，要下模型
rerank API可选如 Cohere / Jina / 国内厂商
matplotlib可选画对比柱状图

为什么先用"字符 bigram"做 BM25

中文没有空格，做 BM25 要先分词。但分词有两个问题：

  1. 要装 jieba（多一个依赖）
  2. 分词错误会直接毁掉检索（"退款流程"被切成"退款/流程"还好，被切成"退/款流/程"就完了）

字符 bigram 是个聪明的偷懒办法：把"退款流程"切成 退款、款流、流程。不依赖词典，对中文效果还不错。

这不是最优解，但它是"零依赖、够用、可解释"的解。工程上"够用"比"最优"重要。
