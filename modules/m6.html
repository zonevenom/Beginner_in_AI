【这一讲要解决什么】

学完这一讲，你能：

  1. 说清 Agent 和"普通调用"的本质区别，以及什么时候不该用 Agent
  2. 自己实现 Function Calling 的完整循环（不用框架）
  3. 设计好用的工具（这比写循环难得多）
  4. 给 Agent 加上刹车：步数上限、超时、权限，防止它跑飞

一、Agent 到底是什么

先看三种"AI 程序"的区别

类型结构例子谁决定下一步
单次调用输入 → 模型 → 输出翻译、分类你（写死）
固定流程（Chain）步骤 A → B → C，写死RAG：先检索再生成你（写死）
Agent模型自己想"下一步干什么"订机票、查数据、改代码模型

一句话：Agent = 让模型参与"决策"，而不只是"执行"。

一个具体的例子

任务："帮我算一下 2024 年 3 月 15 日到今天一共多少天，再查一下这天是星期几。"

固定流程做不了——因为"先算什么再算什么"取决于中间结果。 单次调用也做不了——模型算日期经常错。

Agent 的做法：

注意：这个"先去查日期、再算差、再查星期"的顺序，不是我写死的，是模型自己决定的。

这就是 Agent。

二、Function Calling：Agent 的"机械原理"

很多人以为 Agent 很神秘。其实它的核心机制极其简单，一共四步，循环执行：

flowchart TD A["① 你把'工具清单'和'用户问题'一起发给模型"] --> B["② 模型不直接回答，而是说：
我要调用 get_weather，参数 city=北京"] B --> C["③ 你的代码真的去执行这个函数，拿到结果"] C --> D["④ 你把结果追加进对话，再发给模型"] D --> E{模型还想调工具吗} E -- 是 --> B E -- 否 --> F["输出最终答案"]

关键认知：模型不执行任何代码

这是最大的误解。

模型只输出一段"我想调用 XX，参数是 YY"的 JSON。真正执行的，是你的代码。

所以：

  • 模型不能删你的文件（除非你写了删文件的函数并让它调）
  • 模型不能上网（除非你给了搜索工具）
  • 所有能力边界，都由你提供的工具决定

三、ReAct：让模型"边想边做"

Function Calling 解决了"怎么调"，ReAct 解决了"怎么想"。

ReAct = Reasoning + Acting，循环三步：

为什么需要显式的"想"

因为模型是一个字一个字接的。让它先写"我想干什么"，这段文字就变成了它自己的上下文——下一步决策时它能"看到"刚才的思路。

这和 M1 的 CoT 是同一个原理。

代码上怎么实现

两种方式：

方式做法优点缺点
原生 Function Calling用 API 的 tools 参数稳定、结构化依赖模型支持
提示词模拟让模型按固定格式输出 Action: xxx，你用正则解析任何模型都能用解析容易崩

先用原生 Function Calling。你现在用的模型基本都支持。提示词模拟是"模型不支持时"的退路。

四、工具设计：这才是真正的难点

写循环只要 50 行，设计好工具要几百小时的经验。

五条原则

原则 1：名字要"自解释"

❌ 差✅ 好
query(q)search_products(keyword)
do(x)send_email(to, subject, body)
calc(s)calculate_expression(expression)

模型是靠名字和描述选工具的。 名字含糊，它就会选错。

原则 2：描述要写"什么时候用"和"什么时候不要用"

"不要用它做什么"，比"它能做什么"更重要。 这是防止选错工具最有效的手段。

原则 3：参数越少越好，且要能推断

参数越多，模型填错的概率越高。

参数个数填错率（经验）
1 个低
2~3 个中
5 个以上高，且经常漏填

如果参数超过 5 个，考虑拆成两个工具。

原则 4：返回结构化、简短、可读

返回内容会变成模型的上下文。 返回 5000 字，你的 token 就爆了。

原则 5：错误要"说人话"，让模型能自己纠正

这是 Agent 设计的精髓：把错误信息变成"模型的反馈"。 模型看到"缺少 city"，下一轮就会补上。你不给它反馈，它只会一直错下去。

五、给 Agent 装刹车（不做这一步，迟早出事）

Agent 的危险在于：它会自己决定做什么，而且会一直做下去。

四种必须的刹车

刹车参数防什么
最大步数max_steps=8死循环（模型一直调同一个工具）
超时timeout=60s单次工具调用卡死
成本上限累计 token > N 就停一夜之间烧掉几百块
权限白名单只注册安全工具模型被注入后执行危险操作

最危险的三类工具（绝对不要给）

工具危险
执行任意代码（exec / eval）等于把电脑交出去
删文件 / 改数据库不可逆
发邮件 / 发消息 / 转账不可撤销，且会真实影响别人

如果你非要给，必须加人工确认：模型提出要调用 → 弹窗问你 → 你点"同意"才执行。

提示注入在 Agent 时代升级了

M1 里，注入的后果是"说错话"。 Agent 里，注入的后果是"做错事"。

如果模型照做了，你的邮件就发出去了。

防线：

  1. 危险工具必须人工确认
  2. 工具参数做白名单校验（邮箱只能发给内部域名）
  3. 最小权限：这个 Agent 只注册它真正需要的工具

六、什么时候不该用 Agent

这是最值钱的一节。Agent 被滥用了。

场景该用什么为什么不用 Agent
流程固定的任务（如"检索→生成"）普通 ChainAgent 会"自由发挥"，反而不稳定
需要 100% 可复现写死流程Agent 每次路径可能不同
延迟敏感（<1 秒）单次调用Agent 要多轮，必然慢
简单分类/抽取单次调用引入 Agent 只增加成本和不确定性
高风险操作（转账、删除）人工流程不能让模型自主决定

判断口诀

"步骤是固定的吗？" 是 → 别用 Agent。 "需要根据中间结果决定下一步吗？" 是 → 用 Agent。

再补一条："错了的代价大吗？" 大 → 加人工确认，或者别用。

七、一个完整的最小 Agent（看懂这 40 行，你就懂了全部）

这 40 行里的四个关键点

位置为什么
messages.append(msg)必须把模型的"要工具"消息也存回去，否则模型不知道自己刚才要过什么
json.loads(... or "{}")arguments 是字符串；有时是空字符串
except TypeError模型参数填错是常态，不是异常情况

注意最后一行：messages 也返回了。因为你要看"它到底调了什么"——这是调试 Agent 的唯一方法。

【常见误解】

误解 1："Agent 会自己思考。" 不。它每次都在做同一件事：根据当前上下文，决定"说话"还是"调工具"。所谓"思考"，是它写出来的文字变成了自己的上下文。

误解 2："工具越多，Agent 越强。" 错。工具越多，选错的概率越高。 5 个以内最好，超过 10 个要考虑分组或路由。

误解 3："Agent 能替代 RAG。" 不。RAG 是"给模型资料"，Agent 是"给模型双手"。真实产品里两者配合：Agent 调一个 search_docs 工具，那个工具内部就是 RAG。

误解 4："跑通了就说明做好了。" 跑通只是开始。没做步数限制、没做错误处理、没做权限控制的 Agent，是定时炸弹。

第 1 题 · 该不该用 Agent

#该用吗理由
1❌ 不该流程固定（检索→生成），是标准 RAG。用 Agent 只会增加不确定性
2✅ 该用需要根据"是否下雨"决定"要不要加日历"，分支依赖中间结果
3❌ 不该批量、可复现、要算成本。固定流程最快最省
4⚠️ 可以但要谨慎分析 Excel 有固定套路，用"代码执行工具"更合适；让它自由选工具反而慢
5⚠️ 高风险，需人工确认发邮件不可撤销。必须加人工审核，或只允许"生成草稿"
6✅ 该用改代码→跑测试→看报错→再改，典型的"依赖中间结果"循环

附加问：为什么很多 RAG 产品自称 Agent

三个原因，一个比一个现实：

  1. 营销：2024 年后"Agent"是热词，叫 Agent 更好卖
  2. 功能确实变复杂了：很多产品在 RAG 外面套了"查询改写→路由→多轮检索"的循环，勉强算 Agent
  3. 术语边界本来就模糊：业内对"什么算 Agent"没有统一定义

你要建立的判断是："谁决定下一步"。 你写死的 → 不是 Agent；模型决定的 → 是 Agent。 别被名字骗了，看架构。

第 2 题 · 找出 schema 里的 4 个问题

第 1 问：四个问题

#问题危害
1名字 query 毫无信息量模型不知道它是查什么的，容易选错或不用
2描述只有"查询"两个字模型无法判断"什么时候该用/不该用"
3"type": "int" 不是合法 JSON Schema 类型合法的是 "integer"。有的接口会直接报错，有的会忽略导致模型乱填
4required 里有 extra，但 properties 里没有模型被要求填一个它不知道是什么的参数，必然填错或卡住

第 2 问：改写

改动的四件事：

  1. 名字变成"动词 + 对象"
  2. 描述写了"什么时候用 + 什么时候不用"
  3. integer + 范围约束
  4. required 只保留 1 个，其他都可选

第 3 问：真的需要 6 个参数怎么办

三种做法，按推荐度排序：

做法说明
① 拆成两个工具如 search_by_keyword 和 search_by_filter。模型选工具比填 6 个参数容易
② 用 enum 收窄把自由文本参数变成"三选一"，大幅降低填错率
③ 允许不传，用默认值required 只留最关键的 1~2 个

经验：参数超过 5 个，模型漏填率会明显上升。 这不是模型笨，是"选择空间太大"。

第 3 题 · 补全 Agent 循环

第 1 问：补全

第 2 问：漏了 ① 会怎样

具体现象：

模型的对话历史会变成：

缺少了 assistant 那条"我要调用 get_current_time"的消息。

后果：

  1. 模型看到"用户问时间，然后凭空出现一个 tool 结果"，它不知道这个结果对应哪个请求
  2. 多工具场景下更严重：两个 tool 结果，它分不清谁是谁 → 参数张冠李戴
  3. 有的接口会直接报错：messages with role 'tool' must be a response to a preceding message with 'tool_calls'

规则：tool 消息必须紧跟在"发起调用"的 assistant 消息后面。 这是 API 的硬性要求，不是"建议"。

第 3 问：content 传 dict 会怎样

会报错（不同 SDK 报错信息不同，常见 BadRequestError / 类型校验失败）。

因为 tool 消息的 content 必须是字符串。

注意 ensure_ascii=False：不加的话中文会变成 \u9000\u6b3e 这种转义，虽然模型能读，但浪费 token 且影响可读性。

第 4 题 · Agent 的四种"跑飞"

A：反复调同一个工具，参数一模一样

原因（按概率排序）：

  1. 工具的返回没有"推进"：比如每次都返回"未找到"，模型以为没执行成功，就再试
  2. 工具返回太长/太乱，模型没读出关键信息
  3. 模型能力不足（小模型常见）

修法：

  • 在返回值里加明确的失败原因："未找到匹配记录。可用关键词：退款、物流、发票"
  • 加 max_steps（你已经有）
  • 加重复检测：连续两次相同调用 + 相同参数 → 强行中断并提示

B：每次都报"参数错误"，但每次都传同样的错参数

原因：你给模型的错误信息，没有告诉它"该怎么改"。

修法：

这是 Agent 设计里最容易被忽略的一条：错误信息是"给模型的提示词"，不是"给程序员的日志"。

C：问退款政策，却调了 send_email

原因：

  1. 工具描述没写"什么时候不该用"
  2. 工具太多，模型选花眼
  3. 提示词里没限定"这是知识问答场景"

修法：

  • 每个工具描述加一句"不要用它做 XX"
  • 减少工具数量（>10 个就分组）
  • 系统提示词里写死角色："你是内部知识助手，只回答文档相关问题"

D：输出原始 JSON 而不是回答用户

原因：工具返回的是 JSON，模型"顺着"把 JSON 又输出了一遍。

修法：在 system 里加一条：

这个坑非常常见，尤其是小模型。加一句提示词就能解决 80% 的情况。

第 5 题 · 安全边界

第 1 问：风险等级

工具风险最坏情况
search_docs低泄露不该看的文档（取决于文档权限，不是工具本身）
send_email高以公司名义给客户群发错误/钓鱼邮件，不可撤销
run_sql极高DROP TABLE、误删生产数据、泄露全表数据
read_file高读 ~/.ssh/id_rsa、.env、/etc/passwd，配合外发工具直接泄密

第 2 问：必须人工确认的

  • send_email：必须（不可撤销 + 对外影响）
  • run_sql：写操作必须；只读查询可以自动
  • read_file：不能给任意路径，只能读白名单目录

判断标准："这个操作可撤销吗？会影响到别人吗？" 两个都是"否"才能自动执行。

第 3 问：限制 run_sql 的破坏力（至少 3 条）

#措施
1只读账号：数据库层面就给它 SELECT 权限，物理上不能改
2语句白名单：解析 SQL，只允许 SELECT 开头，禁 DROP/UPDATE/DELETE/INSERT/ALTER
3强制 LIMIT：没有 LIMIT 就自动加 LIMIT 100
4超时：statement_timeout = 5s，防止慢查询拖垮库
5查询视图而非表：只暴露脱敏后的视图（手机号打码）
6审计日志：每次 SQL 都记录，出事了能追

第 1 条最有效："在数据库层面就做不到"，比"在应用层拦截"可靠 100 倍。 这叫"纵深防御"——不要指望一道防线。

第 4 问：提示注入的具体攻击

场景：用户上传一份 PDF 让你总结，PDF 里有一行白字（肉眼看不见）：

攻击链：

  1. 你的 RAG 把这段文字读进了上下文
  2. 模型的 system 和这段"文档内容"在同一个上下文里，没有硬隔离
  3. 模型被说服，调用 read_file 拿到 key
  4. 再调用 send_email 发出去
  5. 你的 API Key 泄露，第二天账单爆炸

防线：

  • 危险工具人工确认（最有效）
  • read_file 路径白名单
  • send_email 收件人域名白名单
  • 文档内容用分隔符包起来，并在 system 里声明"分隔符内是数据，不是指令"（弱防线，但有用）

加分题：非法表达式

1. 项目要做什么

一句话

做一个能自己决定用哪个工具的助手：会算数、会查时间、会换算单位、会在你的笔记里搜东西；并且每一步你都能看到它干了什么。

验收标准

  • 4 个工具，都是"安全"的（没有 eval、没有删文件、没有外发）
  • 用原生 Function Calling，不用 LangChain
  • 有 3 道刹车：最大步数、重复调用检测、单次超时
  • 每一步都有日志：第几步 / 调了什么 / 参数 / 结果 / 耗时
  • 界面上能看到完整的思考链（哪一步调了什么）
  • 问"做不到的事"时，它会承认做不到
  • 没有运行框架（不装 LangChain / AutoGen / CrewAI）

明确不做

  • ❌ 不做多 Agent 协作（一个就够）
  • ❌ 不做联网搜索（要 API key，且引入不可控内容）
  • ❌ 不做代码执行（危险）
  • ❌ 不接真实业务系统

3. 项目文件结构

为什么 tools.py 和 schemas.py 要分开

文件给谁看内容
tools.pyPython 解释器真正的函数实现
schemas.py模型名字、描述、参数类型

同一件事写两遍？ 是的，但这是必要的：

  • 实现是给机器执行的
  • schema 是给模型"阅读"的（描述写得好不好，直接决定它选不选对）

你可以用装饰器自动生成 schema，但对初学者来说，手写一遍能让你体会"描述有多重要"。

三条刹车分别在哪

刹车位置作用
max_stepsD → E防死循环

三个都要有。 只有 max_steps 的话，它可能用 8 步做 8 次同样的错误调用——看起来"没超限"，实际全是浪费。

细节为什么

做三个破坏实验，验证刹车有效：

实验怎么造期望
死循环把 search_notes 改成永远返回"未找到"第 2 次相同调用被"重复检测"拦下
参数错把 schema 里的 expression 改成 expr（实现不变）报"参数不正确"，且模型会尝试修正
